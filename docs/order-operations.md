# Фаска и дополнительные операции

23.10.2026. Локальное расширение прежнего Journal, без коммитов, push, PR и
релиза. Новый Workflow в другой рабочей папке не меняется.

## Поведение

«Фаска» — независимая ручная отметка, по умолчанию выключена. В создании,
редактировании и каждой карточке пакета стоит рядом с «Гибкой», перед
комментарием. Переход одиночной формы в пакет сохраняет отметку у первой
карточки; новые карточки её не наследуют. Импорт не угадывает фаску.
Отметка не меняет формулу или стоимость и не запускает перечитывание прайса.
Редактор показывает изменения и учитывает отметку при проверке несохранённых
правок, конфликтах и явном переносе своих правок на чужой снимок.

Колонка «Фаска» рядом с «Гибкой»: ✓ / пусто / ? для неизвестных или устаревших
данных, только чтение. Имеет фильтр «Есть / Нет / Неизвестно», сортировку,
обычные настройки ширины/порядка/видимости с ID `chamfer`. Старый макет не
сбрасывается. «Задание на резку» дописывает `ФАСКА`, а при обеих отметках —
`ГИБКА, ФАСКА`. По последнему уточнению пользователя результат для письма
выводит название станка прописными без слова «резка» перед ним и добавляет
`   ФАСКА`, затем `   ГИБКА` при соответствующих отметках строки. Порядок
отметок постоянный, при снятых флагах хвост отсутствует. Подпись цены —
«Резка:»; суммы выравниваются прежним способом, но ширина определяется
по итоговым строкам после округления и минимума. Например, исходные
0,0001 / 12,3456 / 499,9999 дают одинаковое `Резка: 500 ₽.` без лишнего
отступа. Это заменяет промежуточный вариант без выравнивания. Отступы
остальных полей, порядок строк, text/HTML/RTF и один завершающий LF
сохраняются. Произвольный комментарий в письмо не включается.
Регистр меняется только в результате для письма, после подстановки общего
имени станка и до вычисления отступов. Материал/рабочее имя/записи MDB не
меняются; «Задание на резку» сохраняет свой прежний формат и порядок отметок.
Проверка этого уточнения: 168 целевых Release-тестов успешно, включая точные
строки/отступы, все сочетания пометок, оба порядка строк, один LF, text/HTML/RTF,
общие имена станков и независимость регистра от системной культуры.
Последнее уточнение цены/двоеточия проверено 171 целевым Release-тестом,
включая смешанные цены, дробные/нулевые/отрицательные исторические суммы,
минимум ON/OFF, большие значения, оба порядка строк и форматы копирования.
Если гибка или фаска недоступны либо требуют проверки привязки, результат
для письма не формируется; показывается причина, прежний ручной текст остаётся.

Привязка пометки — хеш даты и номера спецификации, отдельный домен
`Journal.Operations.v1`. Смена станка/цены/материала её не стирает. При смене
номера/даты фаска остаётся в форме и требует подтверждения, до которого
таблица показывает ? и задание не формируется. Неизвестные данные не означают
отсутствие операции.

## Совместная MDB и разные версии клиентов

Создаётся только необязательная `JournalOrderOperations`:

| Поле | Jet |
| --- | --- |
| OrderId | LONG NOT NULL |
| OperationCode | TEXT(32) NOT NULL, сейчас `Chamfer` |
| IdentityHash | TEXT(64) NOT NULL |
| FormatVersion | SHORT NOT NULL, сейчас 1 |

Составной PK — OrderId + OperationCode. Нет строки — нет операции. `Orders`,
`JournalOrderExtras`, `JournalOrderAnnotations` и прайсы сохраняют свои поля,
типы и ключи. Старый EXE и предыдущие альфы не используют новую таблицу;
их строгая проверка прежних пометок продолжает работать. Одновременная работа
разных версий не переносит фаску в старый интерфейс. Изменение старым клиентом
номера/даты делает пометку требующей проверки. Его DELETE может оставить
строку без заявки; она не показывается и не перезаписывается восстановлением.
Известное ограничение привязки при повторном использовании того же ID,
даты и номера такое же, как у гибки. Неизвестная операция/версия блокирует
полную запись, не удаляется и не превращается в false.

После первого явного чтения Windows-источника:

1. Если таблица уже есть, проверяется только её структура. Второму технологу
   не требуется новая миграция, копия или перенос данных.
2. Если таблицы нет, создаётся полная копия MDB
   `*.before-journal-operations-<UTC>-<GUID>.bak` с эксклюзивным файловым
   доступом, затем под исключительным Jet повторно проверяются таблица и
   исходная Orders и выполняется один CREATE TABLE с ключом.
3. При конкурирующей подготовке проверяется результат другого клиента.
   Идемпотентная подготовка ограничена шестью попытками с паузами
   250/500/1000/2000/2000 мс; задержки сетевого I/O/драйвера не входят в эти
   5,75 секунды. Повторы только при явных кодах блокировки через общий
   AccessSchemaContention; пароль, права, неизвестные ошибки и ошибки проверки
   структуры не повторяются. Неоднозначные Jet 3050/3051 без явного кода
   блокировки обрабатываются без автоматических пауз, с возможностью F5.
4. Постоянная занятость, недостаточные права, отказ копии или неизвестная
   структура дают сообщение без изменения существующих данных. Журнал остаётся
   доступным. В форме ввод сохраняется, заявка с фаской до успешной подготовки
   не записывается. Повтор — явный F5/сохранение, при необходимости после
   завершения работы остальных программ. Чужие процессы не завершаются.

Успешная подготовка кешируется на сеанс/источник. Фоновое автообновление
никогда не подготавливает схему. Перед сохранением явно заданной фаски
готовность проверяется повторно. Рабочая пользовательская MDB при разработке
не меняется. Полностью незаметную миграцию при постоянно открытой другим
приложением MDB обещать нельзя: эта подготовка требует краткого
исключительного доступа для согласованной резервной копии и создания структуры.

## Сохранение и транспорт

Операции — отдельное необязательное свойство `OrderRecord` / `OrderSummary`,
входящее в полный снимок, проверки конфликта, создание/редактирование/удаление/
восстановление в той же транзакции. Не повторять запись после неизвестного
commit. Снятие фаски удаляет только её дополнительную строку. БЛЦБ/цвет и
обычные правки сохраняют её. Локальная Linux-копия поддерживает необязательные
операции; MDB на Linux остаётся только для чтения.

Проверка наличия и структуры JournalOrderOperations живёт в Scope одной
операции/транзакции. Пакет использует один Scope для всех вставок и контрольных
чтений; редактор/удаление/восстановление — один для проверки снимка, записи и
readback. Каждая строка по-прежнему читается и сверяется, условный DELETE/INSERT
и общий rollback сохранены. Между соединениями нет глобального кэша: следующая
операция снова проверяет структуру. Неизвестная операция/версия не пропускается.

AccessHost protocol=1: прежние номера сохранены, `PrepareOperations=19`.
`OperationsSupported` и `OperationsPrepared` явно подтверждают возможность
чтения и подготовки. Старый/несогласованный хост не даёт молча сохранить
фаску: полный снимок без поддержки отклоняется, в списке показано ?. Прежнее
подтверждение гибки не подменяет новое. Desktop и AccessHost поставляются
вместе. Проверка установленного x64→x86 хоста включает фаску.

Корзина: записи с Operations используют версию 2; прежние архивы версии 1
без Operations читаются. Это предотвращает восстановление новой копии старой
альфой с незаметной потерей фаски. Сам формат полного OrderRecord сохраняет
исходные значения и цену; восстановление не пересчитывает их.

## Проверки и границы

OrderOperationsTests: независимые флаги, цена, редактор/замена/подтверждение,
пакет, конфликты, JSON/корзина, CSV/неизвестные операции, повторная и
конкурирующая подготовка, ограниченные повторы, права/неизвестная структура/
отмена и отсутствие DDL в фоне. MaintenanceProtocolTests проверяет capability,
неполные ответы и отсутствие отправки создания при неподготовленном хосте.
Формы/таблица/фильтры проверяются в обеих темах, включая сохранённые макеты.

23.10.2026 полный `scripts/check.sh` на Linux завершился успешно:
45 Python-проверок, 1630 .NET-тестов; 16 необязательных и 75 Windows/Jet-тестов
пропущены. Release-сборка без предупреждений и ошибок. Скриншоты новой формы,
редактора и таблицы просмотрены в обеих темах.

NativeOrderOperationsTests добавляет настоящие Jet-проверки последовательных
и одновременных клиентов/блокировки, копии, неизменности прежних таблиц,
транзакций/конфликта/корзины и старых SQL. На Linux они пропускаются. До
публикации обязательны Windows Jet x86, установленный AccessHost и реальная
SMB-копия с прежним EXE и двумя клиентами. Headless и управляемая модель гонки
не доказывают поведение Windows/SMB.
