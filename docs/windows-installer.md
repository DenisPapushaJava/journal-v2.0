# Полный установщик Windows

`Journal-<версия>-win-x64-OfflineSetup.exe` — один файл для первоначальной установки на Windows 10 22H2 / Windows 11 x64. Он содержит приложение, модуль доступа к MDB и оригинальные установщики .NET Runtime 10.0.13 x64/x86. Во время установки скачивания не нужны. Если совместимый .NET 10.0 той же или более новой patch-версии уже установлен, он пропускается. SDK, Office и Access Runtime не устанавливаются.

## Сценарий пользователя

1. Запустить OfflineSetup, выбрать папку приложения (поле и «Обзор»), проверить путь на следующей странице и нажать «Установить». По умолчанию предлагается `%LOCALAPPDATA%\DenisPapusha.Journal`; можно указать другую отдельную пустую папку на локальном диске с правами записи. Это установка для текущего пользователя: Program Files и каталог Windows отклоняются до начала установки; системный режим для всех пользователей ещё не реализован. Если .NET отсутствует, подтвердить обычный запрос Windows на установку компонента; могут понадобиться права администратора.
2. Открыть Journal и выбрать прежний `OrderDB.mdb` через «База данных». Установщик не угадывает сетевой путь и не заменяет базу новым файлом. Старое приложение сохраняется.
3. Следующие версии загружать через колокольчик. Для обновлений используется прежний Velopack/GitHub feed. Полный установщик скачивать заново не требуется, если зависимости не изменились.

Приложение устанавливается в выбранную папку, данные профиля — отдельно в `%LOCALAPPDATA%\Journal`. Папку с файлами старой программы или MDB установщик отклоняет. При повторной установке прежний путь читается из регистрации Velopack и защищён от изменения; для переноса сначала удалите Journal через параметры Windows и установите заново. Для автоматической первоначальной установки доступен `/JOURNALDIR="D:\Journal"`; без параметра повторная установка сохраняет прежний путь. Изменение папки установленного приложения через этот параметр отклоняется. Повторный запуск полного установщика при открытом новом Journal просит сначала закрыть его; старая WinForms-программа этому не мешает. Удаление приложения выполняет Velopack из списка установленных программ; MDB и личный профиль не удаляются. При ошибке компонентов установщик сообщает причину и не запускает установку Journal. Возврат .NET-кода 3010 сохраняет необходимость перезагрузки, принудительная перезагрузка отключена. Уже поставленная общая .NET не удаляется при удалении Journal: она может использоваться другими программами.

## Почему отдельный процесс MDB

Старое приложение собрано как x86 и использует `Microsoft.Jet.OLEDB.4.0`. Jet входит в Windows и доступен только 32-разрядным процессам. Чтобы сохранить этот драйвер без конфликтов с Office, интерфейс остаётся x64, а `AccessHost/Jornal.AccessHost.exe` работает как x86. Это решение совместимости с существующей Jet MDB, а не выбор Jet для новой базы данных. [Microsoft: Jet и разрядность](https://learn.microsoft.com/en-us/previous-versions/troubleshoot/microsoft-365/microsoft-365-apps/access/jet-odbc-driver-available-32-bit-version).

Новый хост переиспользует `AccessOrderReader`/`OleDbOrderBatchEditor`, сортировку, проверку полей, транзакции и конфликты. Один процесс обслуживает один запрос, затем завершается; сервер или системная служба не нужны. Запрос/ответ — версионированный JSON по перенаправленным stdin/stdout UTF-8, без shell, временного экспорта базы и путей в командной строке. Все исходные значения, NULL, Currency и время передаются без изменения. x86 выбирает Jet прежде зарегистрированного ACE; x64-доступ в сборке разработки сохраняет ACE 16/12.

При обрыве процесса после начала отправки записи клиент возвращает `OutcomeUnknown`: запись могла сохраниться, поэтому нужен F5 до следующей попытки. Автоматического повтора записи нет. Ошибка запуска до отправки означает `NotSaved`. Опубликованные Windows EXE ищут .NET в глобальной установке нужной разрядности, поэтому унаследованный `DOTNET_ROOT` x64 не ломает x86-хост. Перед установкой проверяется создание COM-провайдера Jet в поставляемом x86-хосте; при повреждённых/отсутствующих системных компонентах установка останавливается, Office и база не меняются. Jet DLL не копируются и не перерегистрируются.

Поддержка Jet сохранена ради обязательной совместимости со старой MDB. Ограничение Jet на символы пути зависит от системной ANSI-кодировки: английский runner не принимает кириллический путь, но сохраняет кириллические данные. Установщик не переименовывает рабочую базу для обхода этого ограничения. Проверка вашего русского Windows, прежнего пути и совместной работы старого/нового клиента по SMB остаётся обязательным отдельным испытанием.

## Сборка и защита зависимостей

На Windows:

```powershell
python scripts/release.py package --version 2026.1.0-alpha.1 --runtime win-x64 --updates
```

Команда публикует интерфейс x64 и хост x86, создаёт обычный Velopack Setup/feed и полный OfflineSetup в `artifacts/release`. Упаковка Windows выполняется на Windows; с Linux её делает GitHub Actions. `scripts/publish.sh` даёт только папку UI для разработки, без полного комплекта.

Версии, прямые URL и SHA-512/SHA-256 закреплены в `installer/windows/dependencies.json`; бинарные зависимости не хранятся в Git. На этапе сборки проверяются хеш и Authenticode-подпись Microsoft/Pyrsys. Компилятор Inno Setup 6.7.3 устанавливается в изолированную папку `artifacts/installer-dependencies`, его оригинальный установщик также проверяется. Для сборки нужен интернет или заполненный проверенный кеш. [Inno Setup](https://jrsoftware.org/isinfo.php), [загрузка .NET](https://learn.microsoft.com/en-us/dotnet/core/install/windows).

Velopack получает требования `net10.0-x64-runtime,net10.0-x86-runtime`; полный установщик заранее устанавливает обе среды из вложенных файлов. Дальнейшие пакеты содержат код интерфейса/хоста, но не повторяют установщики .NET. При изменении минимальной среды нужно обновить manifest, согласовать требования Velopack и снова проверить первоначальную установку/обновление. Code signing самого Journal требует сертификата издателя и не подменяется подписью вложенных Microsoft-компонентов.

## Проверка

Общие тесты проверяют передачу данных, валидацию, отсутствие процесса при отмене, ошибки запуска и неопределённый исход повреждённого ответа. `scripts/test-offline-install.ps1` предназначен только для изолированного Windows CI: проверяет отклонение занятой папки и корня диска, устанавливает настоящий OfflineSetup в выбранную папку с пробелами/кириллицей, повторяет установку без параметра пути, отклоняет вторую папку установленного приложения, запускает обязательный x64 → x86 сценарий на искусственной MDB, открывает/закрывает окно и удаляет приложение, проверяя сохранность внешней MDB и профиля. Логи и TRX сохраняются как артефакты. Отдельные контуры проверяют нативные транзакции x86 и реальное Velopack-обновление/перезапуск.

Этот CI-контур не заменяет ручную установку в чистой офлайн-VM Windows 10/11, проверку UAC обычного пользователя, рабочего Office и вашей общей папки. Перед массовой раздачей нужен такой прогон; сборка приложения остаётся предварительной по полноте бизнес-функций.

Транспорт ответа AccessHost читает JSON непосредственно из UTF-8-потока с
прежними подтверждениями и защитой от неподтверждённой записи. Устройство,
отмена, проверки и ограничения измерений — [access-host-transport.md](access-host-transport.md).

## Подпись и блокировка запуска

Опубликованные `alpha.2`–`alpha.6` не имеют Authenticode-подписи собственного кода. По письму, переданному пользователем 17.10.2026, SignPath Foundation отклонил бесплатную заявку из-за недостаточной публичной известности проекта; сертификата и подписанного выпуска нет. Наличие зависимостей не снимает запрет запуска. Сбор диагностического отчёта и статус подписи — [windows-signing.md](windows-signing.md). Установщик автоматически сохраняет стандартный лог в папке TEMP; `/LOG="..."` позволяет указать путь явно.

Новый код после `alpha.4` проверяет `AccessHost --probe` до замены приложения, без открытия MDB. Ошибка запуска сохраняет исходный Win32-код: 4551/1260 объясняются как запрет политики контроля приложений, 577 — как невозможность проверить подпись/целостность. Для уже запущенного хоста различаются NTSTATUS `0xC0E90002` и `0xC0000428`; код 3 означает недоступность Jet, а не доказанную блокировку Windows. В журнале установки сохраняются код и системное пояснение. Отсутствие файла, обычный отказ доступа и другие ошибки не объявляются Smart App Control.

При распознанном отказе защиты на странице остановки установки появляется кнопка «Параметры безопасности». Она по явному нажатию открывает документированный `ms-settings:windowsdefender`; если открыть его нельзя, показан путь через «Пуск». В тихом режиме настройки не открываются. Кнопка не создаёт исключение, не меняет сертификаты, UAC или политику Windows. Для корпоративного ПК сообщение предлагает обратиться к ИТ. [Microsoft: URI параметров](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-settings), [коды Win32](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/shared/winerror.h), [NTSTATUS](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/shared/ntstatus.h).

Такая же причина и «Открыть параметры Windows» доступны в новом приложении при загрузке списка, подключении источника, расчёте/сохранении заявки и изменении БЛЦБ. Это необходимо и после обновления через колокольчик, которое не запускает полный OfflineSetup. Блокировка до запуска хоста означает, что запрос на запись не отправлен; при обрыве после отправки сохраняется требование F5 перед повтором. Ввод, прежний источник, список и результат сохраняются. Старые опубликованные версии этим новым поведением не наделяются.

`tests/Fixtures/InstallerDiagnostics.iss` выполняет общие Pascal-функции диагностики на Windows, включая фактический `Exec` отсутствующего тестового EXE. `scripts/test-offline-install.ps1` компилирует и запускает проверку в изолированном CI до полного прогона установки; она не меняет защиту. C#-тесты моделируют отказ CreateProcess и завершение дочернего процесса с полным Windows NTSTATUS, проверяют семантику записи и состояния окон. Это не испытание реальной политики SAC на пользовательском ПК; такой прогон нужен отдельно.
