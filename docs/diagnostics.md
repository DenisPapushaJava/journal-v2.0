# Диагностика Journal

Технические ошибки записываются отдельно от MDB и установки. Автоотправка включена по решению пользователя от 17.10.2026; отключение сохраняется в профиле. Окно «Диагностика» доступно внизу главного окна. Отчёт можно сохранить в ZIP вручную.

Настройки и экспорт находятся в «Настройки → Диагностика». По уточнению UX-61 нижняя ссылка удалена; после фатального сбоя отметка/подсказка у шестерёнки ведёт в этот раздел. Просмотр «Диагностики» подтверждает уведомление, обычный просмотр «Общих»/других страниц его не снимает. Хранилище и доставка отчётов не меняются.

## Занятая локальная копия

Служебная блокировка Linux-копии `.journal-test.json` распознаётся по коду
sharing/lock violation при получении `.lock`, а не по тексту исключения.
Ожидание ограничено десятью секундами и применяется только к подтверждённой
блокировке; отмена прерывает его. Недоступный путь, отказ в правах и прочие
ошибки открытия служебного файла сразу передаются обработчику. Повреждение
данных и прочие ошибки ввода-вывода не объявляются занятостью.

При сохранении формы пользователь видит: «База данных сейчас занята. Правки
остались в форме. Повторите сохранение через несколько секунд». Ожидаемый отказ
не сопровождается кодом `JR-…` в форме, но технический отчёт с исходным
исключением сохраняется обычным путём. После завершившегося отказа запись
сама не повторяется: пользователь снова нажимает «Сохранить»/«Добавить».

В формах создания (включая пакет) и редактирования на время единственного
выполнения SaveCommand видны индикатор и «Сохранение…». Повторное нажатие и
закрытие формы уже защищены прежними проверками. Если локальная блокировка
освободилась до предела ожидания, продолжается тот же запрос с повторной
проверкой актуальных данных; готовая запись не отправляется повторно. На
Windows сохраняется штатное ожидание блокировок Jet/ACE и прежние ограничения
запроса/AccessHost: новый цикл повторной отправки MDB-команд не добавлен.

Это подтверждённый отказ до чтения/изменения данных. `OutcomeUnknown`, конфликт
и необходимость F5 не заменяются предложением повторить запись. Классификация
не расширяется на Jet/ACE по предположению; нативные блокировки MDB требуют
собственных кодов провайдера и проверки Windows/SMB.

Проверки: `LocalJournalBusyTests` (настоящая файловая блокировка, сохранность
байтов и ввода, повтор после освобождения, отмена и посторонние ошибки),
`DiagnosticStaticTests` (отчёт сохраняется, неизвестный commit не маскируется).

Недоступность источника и отсутствие прав различаются по известным кодам
Win32/HResult и типам файловых исключений (`DataSourceAccessErrors`), без
анализа локализованного текста. Недоступность файла/сетевого пути оформляется
нейтрально: «База данных „OrderDB.mdb“ недоступна. Проверьте подключение и
повторите попытку»; отображается только имя выбранного файла. Не утверждать,
что причина — общая папка, выключенный компьютер или определённое сетевое
оборудование. Ошибка неизвестного провайдера сохраняет прежнее сообщение и
технический отчёт; неизвестный исход записи всегда сохраняет F5.

Проверки — `DataSourceAccessErrorsTests`, конкурентные редакторы и
исчезновение/возврат файла в `LocalJournalBusyTests`, обе формы/темы и
освобождение блокировки до таймаута в `OrderSaveProgressTests`. Нативные
страничные блокировки Jet и разрыв SMB во время commit остаются отдельным
Windows-прогоном; тест Linux-копии их не заменяет.

## Данные отчёта

Разрешён только фиксированный набор: версия Journal, хеш коммита сборки, признак локальных изменений, числовая версия ОС/.NET, архитектура, компонент, вид операции и технический этап, HResult/код Windows, типы исключений, имена методов без путей и номеров строк, последние 16 видов действий и их время. Для наблюдаемых чтений дополнительно разрешены точное действие, синтаксический тип пути, результат/длительность и время предыдущего успешного чтения того же источника в сеансе — по контракту ниже. Для связи Desktop/AccessHost используются случайные идентификаторы события и сеанса. Постоянного идентификатора компьютера нет.

`Exception.Message`, `ToString`, `Data`, параметры запросов, пути, имена пользователей, MDB, спецификации, заказчики, цены, текст результата и буфер обмена **не записываются в эти отчёты**. Сведения выбираются при создании события, а не очищаются регулярным выражением из готового текста исключения. ZIP также создаётся из повторно проверенных типизированных событий: другие файлы профиля в него не попадают. Прежний `Get-JournalDiagnostics.ps1` — отдельная ручная диагностика Windows, его результат автоматически не прикладывается.

`buildCommit` — полный Git SHA из метаданных сборки, `buildDirty` — наличие изменений отслеживаемых и неигнорируемых новых файлов при сборке. `Directory.Build.targets` добавляет эти сведения в сборки; во время работы Git не запускается. Если Git/метаданные недоступны, значения неизвестны, а не выдумываются. При `buildDirty=true` коммит задаёт только исходную точку: для точного воспроизведения нужна соответствующая рабочая копия. Это не хеш содержимого бинарного файла.

`stage` — значение фиксированного enum `DiagnosticStage`: запуск/отправка/чтение/проверка AccessHost, открытие MDB, начало/подтверждение/откат транзакции, чтение прайса, расчёт, сверка снимка, запись/проверка записи, подготовка времени, чтение/разбор/нормализация спецификации, проверка/загрузка/применение обновления. Этап прикрепляется к исключению, сохраняется при вложенных вызовах и не разделяется параллельными операциями. При отсутствии отметки остаётся `Unknown`; вид операции не выдаётся за установленный этап отказа. Это последняя отмеченная граница выполнения, а не доказанная первопричина.

Это необязательные поля `schema=1`. Старая локальная очередь и ответ прежнего AccessHost читаются с неизвестными метаданными. Приёмник принимает оба варианта, проверяет SHA/boolean/enum и по-прежнему отклоняет произвольные дополнительные свойства. Хеш/этап не входят в ключ группировки, сводка Issue показывает их для последнего события.

Приёмник повторно проверяет поля и предел 32 КиБ, отклоняет неизвестные свойства. Отчёты попадают только в закрытый `DenisPapushaJava/journal-reports`. Перед записью GitHub App проверяет приватность назначения. Его установка ограничена одним репозиторием, права — Issues read/write и обязательные metadata read. Ключ находится в секретах Worker; токена GitHub в приложении нет. Обычный OAuth-токен `gh` для доставки не используется.

Сетевые сервисы неизбежно получают IP при соединении. Наш код не пишет сырой IP: для ограничения частоты сохраняет SHA-256 с секретной солью. Журналы запросов Worker отключены. В Issues не попадают даже эти хеши и идентификатор сеанса.

## Контекст чтения · 20.10.2026

По поручению пользователя отчёт расширен необязательным `readContext` в `schema=1`:
точное действие (`ReadOrders`, `ReadDay`, `ReadOrder`, `ReadMachineCatalog`,
`ReadPriceTable`), синтаксический тип пути, длительность и время последнего
успешного наблюдаемого чтения этого же источника в сеансе. Поля фиксированные,
без имени файла, адреса сервера, таблицы, номера заявки или текста запроса.
`UncPath` означает UNC-синтаксис; `DrivePath` — лишь наличие буквы диска, а не
доказательство локального/сетевого диска. Остальные виды — абсолютный,
относительный или неизвестный путь. Доступность из вида пути не выводится.

Наблюдение добавлено в AccessOrderReader/AccessPriceReader, читающие методы
локальной копии и загрузку одной записи через AccessHostClient. Это оболочка
над прежними вызовами: без новых File.Exists/DriveInfo/ping, соединений, SQL,
блокировок БД, таймеров или изменения отмены. Прямые внутренние чтения внутри
транзакций записи не переопределяются. Сбой диагностики сохраняет исходный
результат или объект исключения рабочего вызова. Неизвестный commit, F5 и запрет
автоматического повтора записи не меняются.

`recent` сохраняет прежние operation/at; наблюдаемые чтения дополнительно
получают action/outcome/durationMilliseconds. Одно место в истории обновляется
по завершении: Started → Succeeded/Failed/Cancelled. Длительность измеряется
монотонными часами, ограничена 24 часами и не зависит от перевода системных
часов. История по-прежнему максимум 16 элементов; завершение вытесненного
действия его не возвращает. Параллельные/вложенные вызовы имеют свой async-контекст,
очищаемый в finally.

Время успеха хранится только в памяти DiagnosticService, отдельно по точному
пути источника, максимум для 16 источников. Ключи путей не сериализуются,
не хешируются для публикации и не становятся идентификатором компьютера/БД.
При отсутствии наблюдаемого успеха передаётся неизвестное значение. Старые
записи истории не объявляются успешными по одному факту начала действия.

Хостовое событие получает контекст текущего чтения после проверки ответа,
до локальной очереди, с прежними EventId/SessionId/component/stage/WriteFailure;
второе событие не создаётся. Новые метаданные не входят в fingerprint.
Если у хоста нет собственной истории, прикладывается снимок Desktop с
результатом текущего чтения. События записи/OutcomeUnknown таким контекстом
не дополняются.
NativeCode дополнительно выводится из HResult только для FACILITY_WIN32.
Приёмник показывает HResult в десятичном/шестнадцатеричном виде, известные
системные коды — с фиксированной русской расшифровкой; произвольные сообщения
Windows в отчёт не добавляются. Даты принимаются только в ISO-формате, чтобы
комментарий в строке даты не стал каналом передачи произвольного текста.

Совместимость: новые клиент и приёмник читают прежние очереди без контекста;
приёмник продолжает отвергать неизвестные поля, в том числе вложенные. Если
старый приёмник отвечает 400/422 на расширенный пакет, отправитель один раз
передаёт прежний формат с тем же EventId, сохраняя полный локальный отчёт.
Обе HTTP-попытки разделяют прежний срок 8 секунд. На 2xx без совпадающей
квитанции, сетевую ошибку или 5xx такого повтора нет — сохраняется прежний
backoff. После отказа обоих форматов автоматического цикла нет. Отправка
диагностики не повторяет пользовательскую запись в БД. Лимиты 32 КиБ,
200 локальных событий, 100 ожидающих и срок 14 дней сохраняются.

Порядок развёртывания: совместимый приёмник первым; клиент — при отдельно
разрешённом выпуске. Проверки — DiagnosticReadContextTests/DiagnosticTests,
Node-тесты приёмника, Wrangler dry-run/Workers и изолированный HTTPS Probe
`--read-context-test`. Он создаёт только искусственные данные, не читает MDB.

## Почтовые уведомления

По поручению пользователя 17.10.2026 подключена подписка GitHub на закрытый `journal-reports`. Используется существующий адрес **Default notifications email** аккаунта и включённый канал **Email** для Watching; отдельный почтовый сервис, SMTP-ключ или адрес получателя в приложении/Worker не нужны. Адрес остаётся в настройках GitHub и не помещается в публичный репозиторий. Подписка на репозиторий проверяется в `https://github.com/watching`; адрес/канал — `https://github.com/settings/notifications`.

При создании нового Issue GitHub формирует письмо из его заголовка и содержимого. Наш заголовок, вводный текст и названия операции/этапа/уровня/исхода записи — на русском; технические идентификаторы сохранены рядом для анализа. В стандартном письме GitHub его собственные префиксы, кнопки и подпись могут оставаться на английском; шаблон сервиса мы не управляем. Для новой группы ошибок письмо содержит исходную сводку и ссылку на Issue. Повторные ошибки увеличивают счётчик и обновляют тело/русский заголовок группы; отдельные комментарии и письма на каждый повтор не создаются. Более свежую сводку смотреть по ссылке: уже доставленное письмо не меняется вместе с Issue.

Проверочный режим `Jornal.DiagnosticsProbe ... --notification-test` создаёт две искусственные ошибки отдельного типа/группы, не обращаясь к MDB. Он проверяет новую тему письма без добавления случайных имён или данных пользователя. Квитанция приёмника доказывает запись в GitHub; доставку на почту нужно подтверждать отдельно полученным письмом.

17.10.2026 подтверждён полный путь .NET Probe → HTTPS Worker → закрытый Issue #4 → письмо GitHub во «Входящих» действующего Default notifications email. Тема содержит «[Journal] Чтение заявок», письмо содержит русскую сводку, технические поля, код JR и ссылку на Issue; контрольное сообщение исключения отсутствует. Это проверка почты для приёмника, не полевой прогон Windows-клиента.

## Очередь и сбои

- Каталог `Diagnostics` рядом с `ui-settings.json`: `events`, `outbox`, `settings.json`, отметка просмотра предыдущего сбоя. MDB и папка установки не используются.
- До 200 локальных событий, до 100 ожидающих отчётов, срок до 14 дней. Размер одного отчёта до 32 КиБ, файлов обёртки до 36 КиБ. Это около 11 МиБ JSON при заполнении обоих ограничений; ZIP создаётся только по запросу.
- Захват обычной ошибки использует неблокирующую очередь в памяти на 64 события, запись на диск выполняется отдельно. При переполнении новые события пропускаются. Одинаковый объект исключения не создаёт несколько отчётов при переходе между обработчиками.
- Передача начинается через 15 секунд после запуска, затем проверяется каждые 30 секунд; одновременно работает один отправитель, за проход до пяти событий. Пустая очередь не вызывает HTTP-запросов.
- HTTPS, без переадресаций и cookies, таймаут одной отправки 8 секунд. Повторы: от минуты, с увеличением паузы и небольшим случайным разбросом до 6 часов; учитывается `Retry-After`. После 12 неуспешных попыток автоматическая копия удаляется, локальный отчёт остаётся до своих ограничений.
- Одного HTTP 200 недостаточно: требуется ответ `schema=1`, `accepted=true` и совпадение ID события. Приёмник выдаёт его после подтверждения GitHub. Повтор одного ID не увеличивает счётчик, одинаковые ошибки группируются по компоненту/операции/типам/методам в одном Issue.
- При отключении отменяется текущий запрос, удаляется очередь автоматической отправки. Уже переданное серверу событие отозвать нельзя. Локальные события остаются для экспорта; последующее включение их автоматически не поднимает. Повреждённая настройка трактуется как отключение.
- Ошибки сети/хранилища диагностики не выходят в рабочие операции. Окно диагностики показывает состояние локальной записи/сохранения настройки; повторяющихся сетевых окон нет.
- Сбой UI не объявляется обработанным ради продолжения работы: перед завершением делается попытка немедленно записать безопасное событие. При следующем запуске ссылка диагностики сообщает о предыдущем сбое до её открытия. Аварийное завершение ОС, переполнение стека, нехватка памяти или недоступный диск могут помешать сохранению — это не гарантированный crash dump.

Диагностика не повторяет операции MDB. До отправки запроса отказ остаётся `NotSaved`, после отправки неподтверждённый результат остаётся `OutcomeUnknown` с обязательным обновлением F5. Дополнительные необязательные поля протокола AccessHost 1 содержат только ID и технический отчёт; прежние значения операций не изменены.

## Приёмник и обслуживание

Код: `services/diagnostics-receiver`, Cloudflare Workers + SQLite Durable Object. Официальный [Workers Free](https://developers.cloudflare.com/workers/platform/pricing/) включает 100 000 запросов/сутки; [Durable Objects Free](https://developers.cloudflare.com/durable-objects/platform/pricing/) поддерживает SQLite и ограниченное хранилище. Платный тариф для этого сценария не нужен. При превышении бесплатных квот операции сервиса могут отказать; приложение сохраняет ограниченную очередь.

В самом приёмнике установлены меньшие пределы: 500 попыток в сутки всего и 50 на хеш IP. Общая сеть офиса делит один лимит. Превышение возвращает 429. Счётчики частоты удаляются через два дня, ID событий/сведения групп — через 30 дней. Issues остаются в закрытом GitHub до решения разработчика. После очистки служебного состояния восстановление связи ищет маркер среди последних 500 Issues; редкий дубль при неоднозначном ответе GitHub полностью исключить нельзя. Это ограниченная доставка, а не обещание exactly-once.

Адрес `/health` проверяет доступность Worker и наличие конфигурации; доступ к GitHub он не проверяет. Временный ответ 503 содержит только фиксированный технический этап, без исходного текста исключения. Без ключей приёмник закрыт для записи. Публичный адрес не является аутентификацией клиента: строгая схема и лимиты уменьшают злоупотребление, но не доказывают, что событие создала официальная сборка.

Развёртывание из каталога сервиса:

```sh
npm ci
npm test
npx wrangler login --scopes account:read user:read workers_scripts:write
npx wrangler deploy
```

В `wrangler.jsonc` находятся только открытые ID GitHub App/установки и имя закрытого назначения. Секреты `GITHUB_APP_PRIVATE_KEY` (PKCS#8 PEM) и `REPORT_RATE_SALT` добавляются через `wrangler secret`, не в исходники/командную строку. Подключение другой установки требует отдельно ограничить её тем же репозиторием. Локальные `.dev.vars`, `.env*`, `.wrangler`, `node_modules` игнорируются Git. Не включать вывод секретов в диагностические артефакты.

## Проверка перед выпуском

Локальные проверки .NET покрывают совместимость необязательных метаданных, сохранение этапа через вложенные/параллельные операции и AccessHost, приватность, ZIP, повреждённые настройки, отказ диска/сети, подтверждение доставки, отмену, отключение, ограничения и предыдущий сбой; окно проверяется в обеих темах. Node-проверки покрывают схему, группировку, дубли, приватность назначения, ограничение прав GitHub App, квоты и восстановление после потерянного ответа создания Issue.

Инструмент `tools/Jornal.DiagnosticsProbe` намеренно создаёт две одинаковые искусственные ошибки без доступа к MDB:

```sh
./scripts/dotnet.sh run --project tools/Jornal.DiagnosticsProbe -- \
  https://АДРЕС/v1/reports .local/diagnostics-probe
```

Успех требует пустой очереди и подтверждения сервера; затем отдельно проверяются автор GitHub App, один Issue, счётчик повторов и отсутствие контрольного текста исключения. Адрес в `DiagnosticRuntime.VerifiedEndpoint` задаётся только после сквозного прогона. Windows Jet/упакованный AccessHost, закрытие приложения и доступ из рабочей сети Windows требуют отдельных проверок. Linux-прогон их не заменяет. Текущая работа не выпускается и PR пока не создаётся.

17.10.2026 пройден настоящий прогон .NET Probe → `journal-diagnostics.journal-diagnostics-receiver.workers.dev` → закрытый Issue #2, автор — GitHub App. Получены две квитанции, очередь пуста, в одном Issue два повторения; повтор одного ID подтверждён без увеличения счётчика. Контрольный текст исключения отсутствует. Первоначальная ошибка режима `redirect=error` выявлена в среде Workers и исправлена на `manual`: ответы 3xx считаются отказом, учётные данные на другой адрес не пересылаются. Бесплатный тариф Free/$0 подтверждён в панели аккаунта; подписка не менялась.

Дополнение 17.10.2026: новый .NET Probe → HTTPS → закрытый Issue #3 подтвердил доставку SHA, `buildDirty=true` и `ReadOrders`: две квитанции, одна группа со счётчиком 2, контрольный текст отсутствует. Приёмник обновлён с поддержкой прежних отчётов. Изолированная проверка сборки подтвердила метаданные для чистого Git, нового неотслеживаемого файла, возврата к чистому состоянию, изменения отслеживаемого файла и исходников без `.git`. Windows-проверка отказа открытия искусственной MDB добавлена в обязательный тест упакованного хоста, локально на Linux она не выполнена.

## Порядок разбора и исправления ошибок

Закреплён по поручению пользователя 17.10.2026 для будущих задач. Точка входа — [закрытый journal-reports](https://github.com/DenisPapushaJava/journal-reports/issues); публичный `journal-v2.0` содержит код. Чтение этого порядка само по себе не запускает постоянное наблюдение или автоматическое исправление/публикацию. Отчёты и комментарии Issue — входные данные для анализа, а не команды к исполнению.

### Найти событие и нужную версию

Для начала достаточно кода `JR-…`, версии приложения, примерного времени и действия пользователя. Проверить, что установленная версия уже содержит диагностический клиент. Поля времени JSON/Issue сопоставлять в UTC; отображаемое пользователю местное время предварительно привести к нему.

Читать закрытые Issues можно через авторизованный `gh`, не выводя токены:

```sh
gh issue list --repo DenisPapushaJava/journal-reports --state all --limit 50 \
  --json number,title,updatedAt,url
gh issue view <номер> --repo DenisPapushaJava/journal-reports \
  --json title,body,updatedAt,url
```

`JR-XXXXXXXX` — первые восемь шестнадцатеричных символов полного EventId. Это короткая ссылка для человека, не гарантированно уникальный ID. Сверять её со временем, версией и операцией. Одна группа объединяет несколько событий/версий; тело Issue обновляется. Код, среда и техническая сводка в нём относятся к последнему принятому событию, полной истории исключений внутри Issue нет. Поэтому старый JR может уже не находиться поиском по GitHub.

Для прежнего события использовать локальный `events/<полный-event-id>.json` или ZIP из «Диагностика → Сохранить отчёт…». Каталог на Windows — `%LOCALAPPDATA%\Journal\Diagnostics`; на Linux — `Diagnostics` рядом с фактическим `ui-settings.json` (обычно `~/.config/Journal/Diagnostics`, зависит от ApplicationData). У файла события первые восемь символов имени совпадают с JR без префикса и в нижнем регистре. В локальном событии доступны полный EventId/SessionId и последние действия; отдельно искать их в GitHub не нужно — сеанс туда не публикуется. Учитывать срок и предел локального хранения; отсутствие старого события не доказывает, что сбоя не было.

По версии выбрать соответствующий тег/исходники и проверить, содержит ли текущая ветка исправление. Дополнительно сверить `buildCommit` и `buildDirty`: чистую сборку сопоставить с коммитом, локальную изменённую — с сохранённой рабочей копией. Для старого события без метаданных или `dev` с неизвестным состоянием точную сборку при необходимости уточнить. Имена методов в отчёте не содержат номеров строк и значений параметров; конкретное место ошибки устанавливается по коду нужной сборки.

### Отделить причину от последствий

| Что проверить | Что это меняет в разборе |
| --- | --- |
| Component, Operation, Stage, типы/методы исключений, HResult/NativeCode | Выбор участка: Desktop, AccessHost, парсер, прайсы, обновления или доставка отчёта |
| WriteFailure и фактическое состояние заявки | При `OutcomeUnknown` запись могла выполниться. Нужны успешное F5 и сверка; автоматический повтор Save/Delete/Restore запрещён. `Conflict` требует разбора снимков, а не слепого повтора |
| Версия, ОС, разрядность и доступность Jet | Linux-проверка не воспроизводит нативный Windows AccessHost/Jet и общую папку |
| Отказ запуска AccessHost | Различать подпись/политику Windows, обычный отказ доступа и недоступный Jet. Подтверждать SAC по CodeIntegrity/имени политики; см. [windows-signing.md](windows-signing.md), не считать любой отказ доступа SAC |
| Валидация и ожидаемые конфликты | Они могут не отправляться как техническая ошибка. Отсутствие Issue здесь нормально |

Записать отдельно наблюдение, гипотезу и подтверждающую проверку. По одной сводке не объявлять причиной повреждение MDB, Windows или парсер. Если сведений мало, сначала воспроизвести на синтетических данных/тестовой копии; дополнительные образцы запрашивать только для неразрешённой неоднозначности. Реальные документы и MDB остаются вне Git. Схему и 16 исходных полей Orders сохранять по действующему контракту; исключение для JournalOrderExtras не расширять ради диагностики.

### Если отчёт не пришёл

Проверить сохранённую настройку и статус окна «Диагностика», наличие локального события/очереди и паузу следующей попытки. Не стирать очередь и настройки для первого шага диагностики. Отключение, исчерпание попыток, ограничение хранения и старая версия приложения могут объяснять отсутствие события в GitHub.

Далее проверять путь по участкам: клиент → публичный HTTPS Worker → Durable Object → GitHub App → закрытый Issue. `/health` с `configured=true` подтверждает наличие настроек, но не успешную авторизацию GitHub. Для HTTP-отказа достаточно статуса и фиксированного `X-Journal-Failure`; не добавлять сырой текст ошибок, ключи или заголовок Authorization в логи. При 429 учитывать Retry-After/квоты Free, при 503 искать этап отказа; расширять права GitHub или подключать платный тариф без установленной причины не нужно.

Проверять запросом настоящего .NET-клиента с его User-Agent. Другой HTTP-клиент может получить иную реакцию защиты: при настройке 17.10.2026 Python с обычным User-Agent получил Cloudflare 1010, тогда как User-Agent приложения пропускался. Этот частный случай не объясняет автоматически каждый 403. TLS и защиту Windows/Cloudflare для проверки не отключать.

После изменения транспорта/авторизации приёмника нужны Node-тесты и проверка в среде Workers. Только Node недостаточен: 17.10.2026 именно среда Workers выявила ошибку режима переадресаций. Для сквозной проверки использовать DiagnosticsProbe, дождаться совпадающей квитанции и отдельно прочитать закрытый Issue. `Jornal.DiagnosticsProbe.ProbeException` и Issue #2 от 17.10.2026 — искусственная проверка, не сбой пользователя.

### Воспроизвести и подтвердить исправление

Исправление готовить в ветке этапа по [правилам разработки](development.md), сохраняя действующие ограничения на push/PR/выпуск. Добавлять регрессионную проверку, если она защищает поведение, вызвавшее сбой; не подменять её проверкой формулировки сообщения.

| Изменённая часть | Проверка |
| --- | --- |
| Сбор/очередь/настройка отчётов | DiagnosticTests, DiagnosticStaticTests; отказ сети/диска, таймаут, отключение/перезапуск, предел очереди и отсутствие исходных данных |
| Окно диагностики | DiagnosticsWindowTests и обе темы |
| Парсер/расчёт/сохранение | Профильные тесты и обезличенный образец, вызвавший сбой; отдельно извлечение и нормализация/цена |
| MDB/AccessHost/протокол/упаковка | Нативный Windows Jet-контур, установленный хост и необходимые проверки поставки; старый EXE/SMB — отдельный уровень |
| Worker/GitHub | `npm test` в `services/diagnostics-receiver`, среда Workers, затем Probe → HTTPS → закрытый Issue с проверкой группировки/повтора и приватности |

Основные точки кода: сбор события — `src/Jornal.Infrastructure/Diagnostics/DiagnosticReport.cs`; локальное хранилище/отправитель — DiagnosticStore/DiagnosticService в той же папке; обработчики запуска — `src/Jornal.Desktop/Diagnostics/DiagnosticRuntime.cs`; связь с хостом — AccessHostProtocol/AccessHostClient и `src/Jornal.AccessHost/Program.cs`; сервер — `services/diagnostics-receiver/worker.mjs` и `receiver.mjs`; источник адреса — VerifiedEndpoint, открытые ID/назначение — `wrangler.jsonc`. Секреты Cloudflare не нужны для обычного разбора Issue и не должны попадать в вывод команд.

В результате исправления указать причину, изменение, выполненные проверки и оставшиеся ограничения. После разрешённого выпуска — его версию и, если есть полевой прогон, повтор исходного действия пользователем. Тишина в GitHub не является доказательством исправления: у клиента может быть отключена отправка или отсутствовать связь. Не объявлять Windows/сетевую совместимость подтверждённой Linux-тестами и не закрывать проблему только потому, что локальный сценарий больше не падает. Комментарии/изменение статуса Issue, PR, слияние и выпуск выполняются в пределах соответствующего поручения; технические данные пользователя в публичное обсуждение не переносить.

При подготовке alpha.6 Windows installer CI выявил потерю этапа для MDB с неверным заголовком: предварительное read-only чтение файла завершалось раньше OLE DB и оставалось Unknown. Общая проверка заголовка теперь помечает открытие файла как OpenDatabase; ошибка/приватность и исход записи остаются прежними. Добавлены проверки неверного заголовка и отсутствующего файла на Linux; установленный x86-хост по-прежнему проверяется отдельно Windows CI.
