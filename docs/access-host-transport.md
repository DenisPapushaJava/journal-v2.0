# Потоковый ответ AccessHost

Реализовано локально 19.10.2026. `OrderDB.mdb`, SQL, транзакции, DTO, номера
операций и JSON-протокол `1` не меняются. AccessHost по-прежнему выполняет один
запрос в отдельном процессе Windows x86; интерфейс остаётся x64.

## Чтение и завершение

`AccessHostClient` передаёт stdout.BaseStream непосредственно в
`JsonSerializer.DeserializeAsync<AccessHostResponse>`. Целая UTF-16-строка
ответа и её обратное преобразование в UTF-8 больше не создаются. Готовые
заявки и массив результата по-прежнему находятся в памяти.

stdout, stderr и завершение процесса наблюдаются одновременно, начиная до
отправки stdin. stderr вычитывается в `Stream.Null` с буфером 4096 байт:
содержимое не использовалось клиентом и не должно попадать в телеметрию.
Ожидание отправки/завершения прерывается при ошибке любого читателя.
Простой `WhenAll` здесь недостаточен: парсер может остановиться раньше,
чем дочерний процесс допишет ответ, и хост заполнит канал stdout.

В общем finally запускается отмена внутренних I/O, сразу запрашивается
завершение только собственного живого процесса через `Kill()`. Его фактический
выход ожидается отдельно с новым токеном, независимым от отменённого запроса.
Общий предел очистки — три секунды; он охватывает ожидание выхода, callbacks
отмены, все начатые I/O и освобождение собственных pipe. Отмена запроса
не отключает эту проверку выхода. Ожидание callbacks не предшествует остановке:
callback тоже может ждать освобождения канала.

Полученные клиентом stdin/stdout/stderr освобождаются явно через базовые
потоки: `Process.Dispose` оставляет их владельцу. После ошибки отправки
буфер `StreamWriter` повторно не сбрасывается. Ошибки каждой задачи очистки
наблюдаются, включая поздние завершения после истечения предела, и не
подменяют первоначальный отказ. Если ОС не позволила остановить хост,
исходная операция остаётся неуспешной; выход/откат не объявляются доказанными.

Общий предел остаётся две минуты. Внутренний параметр времени используется
только тестами, пользовательской настройки нет. Блокировки запуска/известные
Windows exit codes проверяются прежним способом. Разбор JSON помечает
`ValidateAccessResponse`; ошибки транспорта сохраняют этап отправки/чтения.

## Целостность и совместимость

До возврата результата обязательны EOF, завершение процесса с кодом 0,
прежняя проверка протокола, данных, подтверждений и диагностики. Готовый
JSON без EOF или с неуспешным exit code не подтверждает операцию. Частично
полученные заявки не передаются интерфейсу. Старый список при ошибке
сохраняется существующим механизмом загрузки.

До отправки записи отказ остаётся NotSaved, после начала отправки
неподтверждённый исход — OutcomeUnknown/F5. Подтверждённые хостом ошибки,
конфликты и изменения прайса проходят прежние проверки. Автоматического
повтора операций MDB нет.

Стандартные JSON-настройки, Unicode, decimal, даты, NULL, неизвестные
необязательные поля, UTF-8 BOM и пробелы сохраняются. Повреждённый UTF-8
теперь отклоняется: прежний StreamReader мог молча заменить неверные байты
символом U+FFFD. Рабочий AccessHost явно пишет корректный UTF-8 без BOM.

Сериализация ответа на стороне AccessHost пока прежняя. Постоянный процесс,
новый протокол, публикация отдельных строк, собственный JSON-парсер,
принудительная GC и изменения кэша истории этим этапом не вводятся.

## Проверки

`AccessHostStreamingTests` проверяет:

- UTF-8/escape/числа на границах порций 1/7/4093 байта, BOM и поля в другом
  порядке, неизвестные поля, точность исходных значений и пометок;
- большой ответ и 2 МиБ stderr через настоящий дочерний процесс;
- пустой/обрезанный/неверный ответ, мусор или второй JSON после первого;
- раннюю ошибку парсера, когда хост не читает большой stdin и заполняет stdout;
- отмену неполного/полного JSON без EOF, таймаут, неуспешный exit code;
- остановку процесса, отсутствие повторной записи и OutcomeUnknown после
  отправки без подтверждения.

`tests/Fixtures/AccessHostProbe` — только тестовая программа без внешних
пакетов; она не входит в Desktop/AccessHost и поставку приложения. Прежние
тесты протокола, прайсов, диагностики и Windows SAC остаются обязательными.
Нативная Jet, упакованный x86-хост, Windows SAC, SMB и старый EXE проверяются
в Windows отдельно; Linux-проверки их не заменяют. Изменение транспорта
требует полного CI поставки по `docs/ci.md` при подготовке публикации.

Исходный этап потокового ответа, 19.10.2026: locked restore и сборка Release успешны,
0 предупреждений/ошибок. Все 21 новые проверки транспорта успешны; полный
набор Jornal.Tests — 1373 passed, 16 skipped, 0 failed, 4 мин 2 с. Пропуски
относятся к Windows/Jet и необязательным частным образцам. Это не результат
нативного Windows CI или полевой проверки общей MDB.

## Контрольное измерение

Linux, .NET 10.0.13, Release, полностью синтетический JSON 17,06 МиБ /
21 910 заявок. Сравнивались прежний клиент из main `b1da083` и новый клиент,
а не только два вызова сериализатора. Оба запускали один и тот же настоящий
дочерний процесс; тот читал запрос и писал один файл порциями 4093 байта.
Проверялось равенство всех заявок. Чтение Jet и работа UI не измерялись.

После прогрева — по 12 чтений каждого варианта с чередованием порядка.
Время измерялось Stopwatch, выделения — GC.GetTotalAllocatedBytes.
Принудительная GC применялась только вне измеряемого участка тестового
инструмента; это не поведение приложения. Тестовый инструмент и исходные
результаты находятся в игнорируемой `.local/access-streaming-benchmark/`.

Обычная конфигурация .NET, медианы:

| Показатель | Прежний клиент | Потоковый клиент |
| --- | ---: | ---: |
| Время обмена и разбора | 176,4 мс | 126,1 мс |
| Новые выделения на чтение | 121,69 МиБ | 23,58 МиБ |

При отключении tiered compilation только в измерительном процессе медианы
составили 233,0 / 185,7 мс и 89,61 / 23,58 МиБ. Состояние ArrayPool влияет
на выделения прежнего клиента: отдельные чтения требуют около 90 или 154 МиБ.
Для небольшого ответа из 50 заявок в обычной конфигурации медианы времени
составили 36,7 / 37,1 мс, выделений — 0,302 / 0,139 МиБ. В этом сценарии
скорость практически одинакова, в неё входит запуск дочернего процесса.
Цифры не являются гарантией ускорения Windows, измерением общего Working Set,
Private Bytes, пика памяти, живого heap или FPS. Для Windows нужно повторить
одинаковый пользовательский сценарий и запись ETL/счётчиков до/после.

## Адресная остановка AccessHost — 19.10.2026

Реализовано локально по отдельному поручению пользователя. Управление жизненным
циклом вынесено в `AccessHostClient.Lifetime.cs`; схема MDB, протокол и правила
исходов записи не меняются. Push/PR/релиз этого этапа не выполнялись.

В Windows-трассе alpha.10 оба всплеска идут через `ReadAsync` →
`AccessOrderReader.ReadCoreAsync` → `OrderDurationPreparingReader.ReadAsync` →
`LoadOrdersScopeAsync`: отменялось чтение полной истории. 960 Win32Exception
возникли внутри обхода дерева процессов в .NET; они не означают 960 ошибок
заявок. События всплесков расположены на 125,859–125,949 и 127,224–127,320
секундах трассы. Это границы зарегистрированных событий, а не замер времени
CPU или длительности всех операций. Стек инициатора отмены в них отсутствует,
поэтому конкретное нажатие или таймаут задним числом не установлены.

Код предусматривает штатную отмену при новой загрузке/F5, смене периода или
поиска, открытии фильтра во время сверки, замене модели/источника, закрытии
окна и отключении автообновления. У фона также есть предел 30 секунд,
у транспорта — две минуты. Сами эти правила данным отчётом не опровергнуты.

В штатной поставке хост — отдельный Windows x86 EXE с `UseShellExecute=false`.
В его коде нет запуска дочерних процессов; Windows-операции выполняются через
OLE DB/ADO/ADOX внутри хоста. Linux `mdb-export` относится к другому пути.
Это контракт адресной остановки: добавление оболочки или дочернего рабочего
процесса в будущем требует пересмотра механизма остановки. Упакованный хост
и его зависимости проверяются Windows-контуром.

Границы реализации:

- Только живой экземпляр `Process`, который запустил этот клиент; поиск по
  имени/PID, `Kill(true)` и запасной обход дерева не используются. Прежний
  путь успеха уже ожидает exit=0/EOF и принудительно не останавливается.
- Порядок начала очистки: `CancelAsync`, адресная остановка, независимое
  ожидание выхода и явное освобождение pipe. Все задачи наблюдаются вместе,
  с единым сроком три секунды. Прежняя задача `exit` с отменённым токеном не
  используется как доказательство выхода. Ошибка очистки не превращает
  неуспешный запрос в успех и не заменяет его первоначальную причину.
- После начала отправки неподтверждённая запись остаётся `OutcomeUnknown`
  с обязательной сверкой F5; выход процесса не доказывает откат транзакции.
  Автоповтора нет; F5/проверка актуальной записи и защита от позднего ответа
  прежнего поколения загрузки сохраняются. Обычная отмена чтения не переводит
  журнал в режим неизвестного исхода записи.

Перед исправлением повторены `AccessHostStreamingTests` и `AccessHostTests`:
32 успешных, 3 Windows-проверки пропущены на Linux. После реализации —
38 успешных и те же 3 пропуска. Прежнее дополнительное ожидание выхода
из теста удалено: теперь сразу после возврата клиента проверяются настоящий
выход процесса и закрытые дескрипторы всех трёх pipe.

Шесть новых сценариев проверяют: только собственный процесс (подменённый
тестовый хост создаёт потомка, который остаётся жив и отдельно убирается
фикстурой); фактический задержанный выход после уже отменённого запроса;
выход между проверкой и остановкой с сохранением исходного JsonException;
отказ и отсутствие эффекта остановки с ограниченным ожиданием/закрытыми
каналами/неизменным OutcomeUnknown; отмену до старта без запуска/остановки.
Прежние проверки полного/неполного JSON без EOF, заполненных каналов,
таймаута, неуспешного exit code и одного запуска сохраняются.

Нативные Windows packaged x86/Jet и повторная трасса требуют отдельного
прогона. Linux не воспроизводит Windows-обход защищённых процессов и SMB.
Классификация точных причин штатной отмены в локальной профилировке остаётся
отдельным улучшением; этот этап не добавляет данные заявок/поиска в диагностику
и не отправляет обычные отмены как ошибки.

Итог адресной остановки 19.10.2026: `scripts/check.sh` успешен — 38 Python-проверок
сценариев выпуска, locked restore, сборка всего решения Release с 0 предупреждений
и 0 ошибок; Jornal.Tests — 1397 успешных, 16 необязательных/платформенных пропусков,
0 ошибок (4 мин 8 с). Все 68 отдельных нативных Jet-проверок штатно пропущены
на Linux. После прогона работающих процессов тестового Probe не осталось;
рабочая MDB и Debug-сборка не менялись. Windows-выигрыш по исключениям/CPU/памяти
ещё не измерен, Linux-тесты не заменяют нативный CI и совместный SMB-прогон.
