# Состав проверок CI

Обновлено 19.10.2026: обязательные `Check (ubuntu-latest)` и `Check (windows-latest)` сохранены. Они являются итоговыми шлюзами и ждут сборки/тесты обеих платформ и отдельный Jet x86. Защита `main` не изменяется.

## Когда выполняются проверки

| Событие / изменение | Проверки |
| --- | --- |
| PR: Markdown, известные настройки VS Code, растровые снимки в `docs/screenshots/` | Быстрые проверки инструментов и настроек, без .NET и упаковки |
| PR: обычный код приложения и тесты | Release-сборка и тесты Linux/Windows; Jet x86 параллельно на отдельном Windows runner |
| PR: поставка, AccessHost/контракт MDB, зависимости, workflow, скрипты, неизвестные пути | Дополнительно упаковка, Windows OfflineSetup, установленный x64-клиент → x86-хост, установка/обновление/перезапуск обеих ОС |
| Push в main после подтверждённого squash PR | Быстрые проверки и проверка наличия кэшей; недостающие зависимости прогреваются один раз, без сборки/тестов приложения |
| Push без подтверждения проверенного PR, недоступный GitHub API | Полный цикл |
| Пустой/неизвестный диапазон PR; ручной CI | Полный цикл |
| Тег выпуска или ручной Release с версией | Полный Release на точной ревизии тега; черновик только после успеха пакетов обеих платформ и Jet |

Классификатор `scripts/ci_scope.py` учитывает полный diff, все коммиты, удаления и обе стороны переименования. Изображения приложения в `docs/design/assets/`, логотипы и неизвестные файлы продолжают требовать полного цикла. Исключение для документации ограничено PNG/JPEG/WebP внутри `docs/screenshots/`; эти файлы не должны включаться в приложение. Смешанный diff получает наиболее полный набор.

## Короткая проверка main

`scripts/ci_verified_merge.py` использует Git и read-only GitHub API. Короткий запуск разрешён только при одновременном подтверждении:

- push содержит один squash-коммит с родителем из `before`;
- коммит связан со слитым PR из этого же репозитория в `main`, база PR совпадает с `before`;
- дерево файлов squash-коммита совпадает с деревом головы PR, а база является её предком;
- последний CI для этой головы PR завершился успешно; оба обязательных Check и определение состава действительно успешны.

При задержке индекса commits/pulls дополнительно просматриваются последние закрытые PR: кандидат обязан иметь точный merge_commit_sha, остальные проверки дерева/базы/CI сохраняются. Для свежего push подтверждение проверяется до четырёх раз с задержками 2/4/8 секунд: метаданные GitHub могут появиться с задержкой. Готовое подтверждение не добавляет ожидания. Недоступный API/токен, неизвестная ревизия, изменение состава при слиянии, прямой push, ошибка/отмена/пропуск проверки после ограниченных повторов дают полный прогон. Данные API не заменяют сравнение Git-деревьев. Токен имеет только `contents`, `pull-requests` и `actions` read; он не записывается в лог или кэш.

Полная история нужна для диапазона diff и проверки дерева; отсутствующую голову PR можно получить по SHA. Отсутствие `pull_requests` в записи workflow run после слияния не считается подтверждением: проверяются PR, его точная голова, workflow и результаты заданий. Более старый успешный запуск не перекрывает последний неуспешный.

## Параллельный Jet и итоговые шлюзы

`.github/workflows/native-access.yml` используется CI и Release. Это отдельный Windows runner с x86 SDK, собственным синтетическим MDB-файлом, обязательным `-RequireProvider` и `JOURNAL_REQUIRE_NATIVE_TESTS=1`. Рабочие MDB не используются. x64-сборке больше не нужно переключаться на x86 SDK и обратно.

Jet запускается для любого кода, независимо от упаковки. При документации/подтверждённом слиянии ожидается его явный `skipped`; ошибка, отмена или неожиданный пропуск не проходят итоговый шлюз. Длинный Build использует `!cancelled()`, поэтому обычная отмена прекращает сборку/тесты. При ошибке scope он всё равно запускает явный отказ gate. Оба коротких итоговых Check запускаются через `always()` и проверяют результат определения состава, результаты всей матрицы Build и Jet. Ошибка определения состава также блокирует слияние.

Пакеты могут собираться параллельно Jet. Публикация черновика Release зависит от **обоих** заданий `package` и `native`, поэтому ошибка Jet блокирует выпуск. Сам Release не использует короткий режим main и не переиспользует PR-пакеты с другой версией/ревизией.

## Кэш

- NuGet: `actions/cache`, ключ по ОС, всем `packages.lock.json` и манифесту dotnet tools; `restore --locked-mode` сохраняется. Кэшируются пакеты в `.nuget/packages`, а не `bin/obj` или готовые сборки.
- Установщик: только исходные скачанные EXE из `artifacts/installer-dependencies/`, ключ по `installer/windows/dependencies.json`. Каждое использование повторно проверяет хеш и Authenticode издателя. Распакованный компилятор Inno Setup не кэшируется. Для Authenticode выбирается установленный PowerShell 7 с возвратом к Windows PowerShell при его отсутствии; унаследованный PSModulePath очищается. Полный CI проверяет download-only из pwsh до долгой сборки/тестов, затем собирает установщик из bash.
- Проверенный main использует `lookup-only`: при попадании SDK и зависимости не скачиваются, при промахе выполняются только restore/tools и загрузка проверенных EXE. Это создаёт кэши в области default branch, доступной будущим PR и тегам. Один кэш внутри PR сам по себе не ускоряет следующие PR/релизы. Jet использует restore-only, чтобы его сокращённый набор пакетов не занял ключ полного решения.
- При отсутствии кэша выполняется обычное скачивание. Секреты и данные пользователей в кэш не входят.

## Время в UI-тестах

Пять сценариев автообновления используют уже существующий `TimeProvider` и управляемую подписку. Часы продвигаются явно, а тот же обработчик проверяет свёрнутое/неактивное окно, фокус письма и открытый фильтр. Производственные интервалы и поведение не меняются. Один отдельный сценарий `RealWatcherAndDispatcherTimerRefreshAnEmptyDay` сохраняет настоящий файловый watcher и DispatcherTimer.

## Проверка изменений

```bash
python3 -m unittest discover -s tests/release -v
python3 scripts/ci_scope.py check
.local/tools/actionlint .github/workflows/modern.yml .github/workflows/release.yml .github/workflows/native-access.yml
```

Тесты используют временные Git-репозитории и подменённый read-only API: успешное слияние, иное дерево/база, прямой push, недоступный API, последний отказ после старого успеха, отсутствие/ошибка/отмена/пропуск обязательного задания. Нативный Jet и установленный MDB-хост проверяются отдельно на Windows. Локальные тесты классификатора не заменяют реальный прогон GitHub Actions.
