# Как ведём разработку

Одна основная ветка **`main`** и ветка на каждый законченный этап. Это простой [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow). `main` выполняет роль «мастера»; отдельные `develop` и ветки релизов не нужны. Уточнено пользователем 16.10.2026: не создавать PR на каждую небольшую правку; сохранять исходные ветки после squash merge.

## Обычная задача

1. Обновить `main` и создать ветку этапа, например `feature/order-form` или `fix/order-date`. Ветки Codex начинаются с `codex/`.
2. Постепенно доработать этап, проверяя через F5 и подходящие тесты. Сохранять небольшие коммиты; ветку можно отправлять на GitHub для сохранности без открытия PR. В текущем CI обычный push в такую ветку без PR не запускает проверки.
3. Когда этап готов к слиянию, создать один PR в `main`: русский заголовок и краткое описание результата и проверок. Связанные уточнения и исправления добавлять в ту же ветку/PR.
4. Дождаться успешного CI на Linux и Windows. Для слияния одобрение второго человека не требуется.
5. Нажать **Squash and merge**. Этап попадёт в `main` одним коммитом; его заголовок и описание берутся из PR. Исходную ветку сохранить на GitHub с подробными коммитами, без переписывания её истории. Автоматическое удаление отключено.
6. Переключиться на `main`, получить изменения и начать следующую задачу в новой ветке.

Пример этапа: форма заявки, расчёт, валидация и несколько уточнений её интерфейса — одна ветка и один PR. Промежуточные результаты показываем пользователю локально; новое сообщение или небольшой коммит сами по себе не запускают создание PR. Несвязанные функции не объединяем в один бесконечный этап. При падении CI исправления отправляются в тот же PR. Если параллельно изменилась `main`, GitHub может потребовать обновить ветку и повторить проверки.

Исправления по техническому отчёту начинаем с [порядка разбора ошибок](diagnostics.md#порядок-разбора-и-исправления-ошибок). Он связывает закрытые Issues, локальные события и код нужной версии; не меняет договорённость о ветках, PR и выпусках.

## Команды

Начало задачи:

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/import-html
```

После изменений:

```bash
./scripts/check.sh
git add src tests
git commit -m "Добавить извлечение полей из HTML-спецификации"
git push -u origin feature/import-html
```

Продолжать итерации в этой ветке до готовности этапа, затем открыть PR и слить после зелёных проверок. `git add` должен включать только файлы своей задачи; пример `src tests` подходит для изменения кода и проверок.

После слияния:

```bash
git switch main
git pull --ff-only origin main
git fetch --prune origin
```

Сохранённую ветку считаем архивом этапа и больше не развиваем. Новый этап начинаем от актуальной `main`. Не передавать `--delete-branch` при слиянии через `gh`; локальное удаление не является обязательным шагом.

При squash создаётся новый коммит в `main`; оригинальные коммиты ветки не становятся его предками. Поэтому `git branch --merged` может не считать её влитой, хотя изменения уже в `main`. Статус завершения проверяем по **Merged у PR**, с указанием ветки и squash-коммита. Не выполнять повторное слияние, rebase или reset сохранённой ветки ради отметки в Git. Продолжение разработки в такой ветке может включить старые коммиты в следующий PR — [описание GitHub](https://docs.github.com/en/pull-requests/reference/pull-request-merges).

## Согласованное разделение CI

Обновлено по поручению 19.10.2026: документация/скриншоты — быстрые проверки; код — сборка/тесты обеих платформ и параллельный обязательный Jet x86; изменения поставки — полный установочный контур. После подтверждённого squash PR на main выполняются быстрые проверки; неподтверждённый push получает полный прогон. Release всегда заново проверяет свой тег и ждёт Jet. Точные условия, кэш и проверка происхождения — [CI](ci.md).

Имена обязательных Check и защита main сохранены. Итоговые шлюзы ждут все требуемые задания и отклоняют ошибку, отмену и неожиданный пропуск. Кэш не заменяет locked restore или проверку подписей зависимостей установщика.

## Основная ветка и выпуски

Защита `main` требует PR и успешные проверки `Check (ubuntu-latest)` и `Check (windows-latest)`. Принудительная отправка и удаление основной ветки запрещены. Настройки владельца позволяют административный обход, но обычный процесс разработки его не использует.

Сообщения коммитов, названия и описания PR — на русском, например «Исправить чтение даты из заголовка». Перед squash merge проверить заголовок PR: он станет заголовком коммита в `main`.

Когда готов выпуск, на проверенном коммите `main` ставится тег вроде `v2026.1.0-alpha.1`. Это отдельное действие: слияние PR само по себе не публикует релиз. [Версии и процесс выпуска](releases.md).

## Постепенный перенос

Первый этап по уточнению пользователя — каркас главного окна на вымышленных данных. После форм, результата и массовых действий в деможурнале подключено чтение настоящей MDB. Далее подключена Windows-запись статусов/БЛЦБ с транзакциями и конфликтами; её нативные тесты — отдельный обязательный проект Jet/ACE x86 в Windows CI. Затем добавлены отдельное чтение прайсов и проверяемый расчёт цены без записи ([контракт](pricing.md)). Для Linux отдельно добавлена редактируемая тестовая копия реальных данных с прайсами, созданием, расчётом, статусами и БЛЦБ ([описание](linux-local-copy.md)). Далее подключено создание с предварительным расчётом и транзакционной записью в MDB ([контракт](manual-orders.md)). Далее добавлены редактирование и локальная корзина с восстановлением/итогами группового удаления ([контракт](order-maintenance.md)); схема MDB сохраняет совместимость с первой программой. Следующие задачи — извлечение спецификаций и остальные функции. Каждый этап сверяем с матрицей старого поведения; чтение/запись реальной MDB и офлайн-установщик требуют отдельной проверки на Windows. Очерёдность следующих задач можно уточнять по результатам просмотра работающего интерфейса.
