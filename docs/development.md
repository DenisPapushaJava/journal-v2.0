# Как ведём разработку

Одна основная ветка **`main`** и короткая ветка на каждую задачу. Это простой [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow). `main` выполняет роль «мастера»; отдельные `develop` и ветки релизов не нужны.

## Обычная задача

1. Обновить `main` и создать ветку, например `feature/import-html` или `fix/order-date`. Ветки Codex начинаются с `codex/`.
2. Сделать изменения, проверить их локально, сохранить коммиты и отправить ветку на GitHub.
3. Создать PR в `main`: русский заголовок и краткое описание результата и проверки. Незавершённую работу можно показать через Draft PR.
4. Дождаться успешного CI на Linux и Windows. Для слияния одобрение второго человека не требуется.
5. Нажать **Squash and merge**. Одна задача попадёт в `main` одним коммитом; его заголовок и описание берутся из PR. GitHub автоматически удалит удалённую ветку.
6. Переключиться на `main`, получить изменения и начать следующую задачу в новой ветке.

Небольшую правку тоже проводим через короткую ветку и PR. При падении CI исправления отправляются в ту же ветку; PR обновляется автоматически. Если параллельно изменилась `main`, GitHub может потребовать обновить ветку и повторить проверки.

## Команды

Начало задачи:

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/import-html
```

После изменений:

```bash
./scripts/check.sh
git add src tests
git commit -m "Добавить извлечение полей из HTML-спецификации"
git push -u origin feature/import-html
```

Затем открыть PR на GitHub и слить его после зелёных проверок. `git add` должен включать только файлы своей задачи; пример `src tests` подходит для изменения кода и проверок.

После слияния:

```bash
git switch main
git pull --ff-only origin main
git fetch --prune origin
```

GitHub удаляет ветку на сервере; локальную завершённую ветку при необходимости можно удалить через IDE после проверки слияния PR.

## Основная ветка и выпуски

Защита `main` требует PR и успешные проверки `Check (ubuntu-latest)` и `Check (windows-latest)`. Принудительная отправка и удаление основной ветки запрещены. Настройки владельца позволяют административный обход, но обычный процесс разработки его не использует.

Сообщения коммитов, названия и описания PR — на русском, например «Исправить чтение даты из заголовка». Перед squash merge проверить заголовок PR: он станет заголовком коммита в `main`.

Когда готов выпуск, на проверенном коммите `main` ставится тег вроде `v2026.1.0-alpha.1`. Это отдельное действие: слияние PR само по себе не публикует релиз. [Версии и процесс выпуска](releases.md).

## Постепенный перенос

Первый этап по уточнению пользователя — каркас главного окна на вымышленных данных. После форм, результата и массовых действий в деможурнале подключено чтение настоящей MDB. Далее подключена Windows-запись статусов/БЛЦБ с транзакциями и конфликтами; её нативные тесты — отдельный обязательный проект Jet/ACE x86 в Windows CI. Создание/редактирование заявок, извлечение спецификаций и расчёты остаются следующими задачами. Каждый этап сверяем с матрицей старого поведения; чтение/запись реальной MDB и офлайн-установщик требуют отдельной проверки на Windows. Очерёдность следующих задач можно уточнять по результатам просмотра работающего интерфейса.
