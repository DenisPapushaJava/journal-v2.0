# Импорт спецификаций: первый HTML-профиль

Реализован отдельный `BlockHtmlSpecificationParser`, профиль `block-html/v1`, для семейства HTML БЛОК/Wintech. Он работает поверх `DocumentReader`, возвращает типизированные поля, источники и сообщения. `BlockSpecificationNormalizer` отдельно готовит прежнее представление заявки и коэффициент. Расчёт цены/запись в MDB остаются другими действиями.

Это этап библиотеки и диагностического инструмента. Импорт в окно новой заявки, перетаскивание, текст из буфера, PDF HansLaser и редактор профилей **ещё не подключены**. Схема MDB и сохранённые заявки этим кодом не меняются.

## Источники полей

| Поле | Источник и правило |
| --- | --- |
| Номер/дата | Ячейка заголовка «Спецификация №». Из идентификатора `yyyy-MM-dd-номер` или `yyyy-MM-dd--номер`; в журнал — `MMdd-номер`. Начальные нули номера сохраняются. Дата печати и внешнее имя файла не используются. |
| Вид резки | Явная метка ЛАЗЕР / ПЛАЗМА / ГАЗО-КИСЛОРОДНАЯ непосредственно после идентификатора в заголовке. Слова дальше в названии и расширение `.rcam`/`.cry` не выбирают станок. Отсутствующая/непонятная метка требует проверки, default-станка нет. |
| Толщина/габариты | Подпись «Габариты» и связанное значение. Порядок документа: толщина × длина × ширина; размер в журнале: ширина `x` длина. Принимаются `x`, `×`, кириллическая `х`, точка/запятая и целая толщина. |
| Листы | Подпись «Листов» в метаданных, положительное целое число. |
| Материал | Пара «Материал»/значение перед колонкой «Одна деталь» в строках детализации либо отдельное поле метаданных. Произвольная марка без пробелов; регистр, кириллица/латиница и `_` сохраняются. Повторяющиеся марки сверяются между собой, указанная рядом толщина — с габаритами. |
| Детали/пробивки/длина/вес | Только таблица итогов с «Всего по заказу». Количество деталей — «Общие кол-во деталей» и явно поддержанные варианты подписи; прочие поля — по своим подписям. Данные отдельных деталей не подменяют итоги. |
| Длительность | Итоговое «Время», `часы:минуты[:секунды]`. Часы не ограничены сутками/неделей; минуты и секунды 0–59, переполнение диагностируется. |

Таблицы и поля определяются по роли и подписям, без фиксированных номеров таблиц/строк и глобального поиска по плоскому тексту. Поддержаны пустые ячейки оформления, перестановка таблиц и пар полей, значение в соседней ячейке или после подписи в той же ячейке. Colspan/rowspan ячеек оформления не сдвигают поиск: подпись и значение связываются внутри одной строки, сетка через несколько строк не достраивается по догадке. Вложенная таблица читается самостоятельно, её текст не входит в значение внешней ячейки. `br`, `p`, `div` сохраняют логические границы текста.

Название детали, даже начинающееся с «Материал», «Спецификация №» или содержащее `Вес`, `кг`, `.rcam`, не читается как итоговое поле. Результаты не привязаны к расширению имени заказа внутри заголовка. Отдельный профиль не заменяет распознавание всех возможных версий отчёта: если структура/метки неизвестны, нужны диагностика и дополнительный образец.

## Неоднозначности и источники

`SpecificationParseResult` содержит значения и `SpecificationIssue` с полем, стабильным кодом и уровнем. Каждый распознанный факт имеет ссылки на таблицу, строку, ячейку (индексы с нуля), подпись и исходный текст. Некорректные/разные значения сохраняют источники в диагностике; первый подходящий кандидат не выбирается молча. Одинаковые повторные значения допустимы, все источники сохраняются.

Обязательные пропуски, неверные числа, разные материалы/габариты/итоги, несколько разных заголовков и противоречие толщины блокируют нормализацию. Ноль не заменяет неизвестное значение; количество деталей/листов должно быть положительным. Не выполняется подмена итоговых пробивок суммой деталей: в предоставленных ранее документах они различаются, причина ещё не подтверждена.

Длительность пока необязательна: её отсутствие/ошибка видны как предупреждение, но не уничтожают достоверно распознанные поля MDB. Она хранится в результате разбора и **не записывается в MDB** — отдельного согласованного поля там нет. Начальные признаки `@`/`*@` оставляют документ вне HTML-профиля БЛОК; будущий HansLaser-профиль должен сохранить их смысл. Префикс, который добавлял старый файловый загрузчик, не внедряется в новые документы.

## Нормализация и расчёт

Сохраняется прежнее правило длины БЛОК: `truncate(мм) / 1000` с целочисленным делением, затем `+ 1`. Для **1000 мм результат 2 м**, это намеренно отличается от `Ceiling`. Нормализатор этого профиля не применяется к HansLaser. Явная подпись метров `(м)` переводится в миллиметры до того же правила; неизвестные единицы не угадываются.

Коэффициент рассчитывается общим `CuttingPriceCalculator.CalculatePunchCoefficient` по **итоговым** деталям и пробивкам, с прежними Double/ToEven и шкалой. Цена здесь не читается и не вычисляется, количество листов не добавляется как новый множитель. Нормализованные размеры, количество листов и вес выводятся числами invariant culture; исходные значения остаются в источниках. Старые строки базы не нормализуются и не пересчитываются.

## Диагностика

```bash
./scripts/dotnet.sh run --project tools/Jornal.Inspect -- \
  block-spec "/путь/спецификация.html" "/путь/другая.htm"
```

Для каждого файла выводится JSON: отчёт/источники/сообщения и нормализованная заявка при полном распознавании. Команда ничего не пишет в MDB или спецификации. Код завершения 1 означает хотя бы один отказ/неполный разбор; остальные переданные файлы всё равно обрабатываются. JSON с реальными значениями сохранять только в `.local/`/закрытую папку, не публиковать вместе с кодом.

## Проверки и дальнейшие шаги

Публичные тесты используют вымышленные документы: долгие и служебные имена, одинарный/двойной дефис, другие расширения, разные материалы, длительность > суток/недели, вложенные таблицы, переносы/пробелы, неоднозначности, отсутствие итогов, неизвестные форматы/маркеры, исходные ячейки и прежнее округление.

Для частного корпуса есть `JOURNAL_BLOCK_SPEC_MANIFEST`: путь к JSON-массиву `{Id, Path, Expected}`, где Expected — `NormalizedBlockSpecification`, значения предварительно сверены по документу отдельно от нового парсера. Опциональный тест сравнивает все нормализованные поля и хеш каждого исходного файла до/после. Корпус и ожидания с реальными данными в Git не входят.

На этой машине старые пути к семи первоначальным HTML сейчас недоступны. Первый прогон выполнен на двух дополнительно найденных старых отчётах — лазер/плазма; это наблюдения по этим файлам, не подтверждение всех первоначальных образцов и не проверка старого EXE на Windows. Для продолжения нужны актуальная папка исходных примеров и проблемные варианты. Следующий этап — просмотр импорта в форме с ручной проверкой, затем отдельный PDF/текстовый профиль и сравнение на расширенном корпусе. Автоматическое обновление существующей заявки по совпадению номера и массовый импорт пока не реализованы.
