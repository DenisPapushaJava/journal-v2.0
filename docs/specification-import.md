# Импорт и распознавание спецификаций

Реализован отдельный `BlockHtmlSpecificationParser`, профиль `block-html/v1`, для семейства HTML БЛОК/Wintech. Он работает поверх `DocumentReader`, возвращает типизированные поля, источники и сообщения. `BlockSpecificationNormalizer` отдельно готовит прежнее представление заявки и коэффициент. Расчёт цены/запись в MDB остаются другими действиями.

Первый этап библиотеки и диагностического инструмента дополнен импортом HTML в окно новой заявки и перетаскиванием (описано ниже). PDF HansLaser подключён отдельным профилем: [источники полей, нормализация и проверки](hans-pdf-import.md). Текст из буфера и редактор профилей **ещё не подключены**. Сам разбор не пишет в MDB; сохранение выполняется отдельным явным действием без изменения схемы.

## Распознавание и расширение профилей

Уточнение пользователя 17.10.2026, UX-41: расширение файла допускает чтение, но не доказывает, что это спецификация. Нераспознанный документ не открывает пустую заявку. Распознанный неполный документ открывает форму с достоверными значениями и пустыми пропусками/конфликтами. Общий `SpecificationParseResult.IsRecognized` независим от полноты полей; `IsComplete` требует и распознавания, и прежних проверок. `SpecificationImportPreview.Create` не принимает нераспознанные отчёты.

`SpecificationProfileCatalog.Default` регистрирует `ISpecificationProfile`: устойчивый Id, понятное название, контейнер DocumentKind, Parse и собственное NormalizeCutLengthMeters. Сейчас это `block-html/v1` и `hans-pdf/v1`. Все профили соответствующего контейнера проверяются; единственный распознавший профиль выбирается, ноль даёт отказ, несколько — неоднозначность. Первый профиль не выбирается по порядку. Имя внешнего файла, одиночное слово или случайный номер не определяют профиль. Для HTML/PDF нет запасного станка или нормализатора: в частности, правило метров БЛОК не подменяет Ceiling HansLaser.

Структурные правила текущих профилей:

- БЛОК: заголовок в своей ячейке вместе с характерным итоговым разделом либо с метаданными листов и детализацией. При отсутствующем/нечитаемом заголовке нужны метаданные листов, детализация и итоги вместе. Метаданные — подписи листов и габаритов; детализация — «Одна деталь»/«Все детали»; итоги — «Всего по заказу» с несколькими полями, включая длину/детали/пробивки. Это признаки структуры, поэтому неверное значение или пропущенный вес не отменяют распознавание.
- HansLaser: итоговая шапка с «Заказ» и несколькими разными показателями резки вместе с таблицей листов (размеры, материал, газ, толщина, количество) либо меткой HANSLASER в ячейке заказа. Некорректная дата заказа остаётся пустой, дата печати её не заменяет. Слова в детализации не создают другую таблицу листов.

Это проверка известной структуры, не подтверждение происхождения/подлинности документа. Правила уточняются по новым образцам, включая отрицательные, без ослабления проверок полей.

### Как добавлять другой вид спецификации

Пользователь ожидает расширение набора видов в будущем. Добавить отдельный профиль с явными структурными признаками и прежними семантическими полями/источниками, определить его нормализацию и зарегистрировать в каталоге. Новый профиль для существующего HTML/PDF использует тот же reader, сервис, форму и DnD. Список расширений/названий ошибки и фильтр выбора файла берутся из каталога; не добавлять новые `if pdf → HansLaser` в UI. При появлении нового контейнера отдельно расширить DocumentKind/DocumentFormats и DocumentReader; регистрация профиля сама по себе не добавляет декодер, OCR или новый расчёт цены. Не угадывать тариф/станок по внешнему имени.

Для каждого нового профиля нужны положительные, неполные, конфликтующие и посторонние документы с похожими словами, проверка неоднозначности с соседними профилями, исходных данных/нормализации и отмены. Существующий корпус должен оставаться распознаваемым; ослаблять проверку всех профилей ради одного нового образца нельзя. Реальные файлы/ожидания остаются вне Git.

### Приём, отказ и ошибки чтения

При наведении проверяются только состав перетаскивания, расширения и доступность операции — без чтения содержимого и сетевого I/O в DragOver. Один допустимый HTML/PDF показывает прежний нейтральный оверлей без текста. Другой тип, папка, набор без поддерживаемых расширений, текущая операция, настройка экрана или источник read-only дают DragEffects.None, мягкий красный оверлей, знак запрета и короткую причину. Уход мыши убирает состояние; нажатие/отпускание не запускает второй импорт.

После отпускания — фоновое чтение с отменой. Отказ распознавания/неоднозначность, недоступный/повреждённый файл, PDF без текстового слоя и лимиты дают карточку с причиной и «Закрыть»/Esc, без новой формы и без подмены ввода, результата или источника. Фокус возвращается к прежнему элементу. В выборе файла внутри формы действуют тот же сервис/распознавание и краткая ошибка; отказ/отмена сохраняют поля, прежний импорт и расчёт. Ожидаемый DocumentRejectedException не отправляется как технический сбой; неожиданные ошибки продолжают получать безопасный JR-отчёт.

Решение реализации: до чтения проверяется предел 50 МиБ, у PDF до обхода страниц — 500 страниц. Значения вынесены в DocumentReadLimits, это не пользовательский раздел настроек. Отмена прекращает ожидание в UI даже при медленном системном открытии файла; она не обещает принудительно прервать заблокированный системный вызов. Поздний результат не открывает форму. HTML не выполняет скрипты и не загружает связанные ресурсы.

Проверка текущего расширения: синтетические чужие HTML/PDF, ключевые слова вне структуры, PDF без текста, частичные отчёты, неоднозначные/дополнительные профили, повреждение/недоступность/лимиты, сохранение формы при отказе и состояния DnD обеих тем. Дополнительно доступный частный корпус 29 HTML + 60 PDF распознан без записи; SHA-256 каждого файла сверяется до/после. `JOURNAL_RECOGNITION_CORPUS` задаёт игнорируемый JSON-массив путей. Это проверка распознавания/неизменности файлов, не новая независимая сверка каждого значения или проверка Windows/SMB.

## Источники полей

| Поле | Источник и правило |
| --- | --- |
| Номер/дата | Ячейка заголовка «Спецификация №». Из идентификатора `yyyy-MM-dd-номер` или `yyyy-MM-dd--номер`; в журнал — `MMdd-номер`. Начальные нули номера сохраняются. Дата печати и внешнее имя файла не используются. |
| Вид резки | Явная метка ЛАЗЕР / ПЛАЗМА / ГАЗО-КИСЛОРОДНАЯ непосредственно после идентификатора в заголовке. Слова дальше в названии и расширение `.rcam`/`.cry` не выбирают станок. Отсутствующая/непонятная метка требует проверки, default-станка нет. |
| Толщина/габариты | Подпись «Габариты» и связанные значения, в том числе несколько соседних ячеек/вариантов в одной ячейке. Порядок документа: толщина × длина × ширина; размер в журнале: ширина `x` длина. Принимаются `x`, `×`, кириллическая `х`, точка/запятая и целая толщина. |
| Листы | Подпись «Листов» в метаданных, положительное целое общее количество. Указанное рядом с отдельным размером количество `шт` сохраняется как дополнительный факт и не подменяет общий итог. |
| Материал | Пара «Материал»/значение перед колонкой «Одна деталь» в строках детализации либо отдельное поле метаданных. Произвольная марка без пробелов; регистр, кириллица/латиница и `_` сохраняются. Повторяющиеся марки сверяются между собой, указанная рядом толщина — с габаритами. |
| Детали/пробивки/длина/вес | Только таблица итогов с «Всего по заказу». Количество деталей — «Общие кол-во деталей» и явно поддержанные варианты подписи; прочие поля — по своим подписям. Данные отдельных деталей не подменяют итоги. |
| Длительность | Итоговое «Время», `часы:минуты[:секунды]`. Часы не ограничены сутками/неделей; минуты и секунды 0–59, переполнение диагностируется. |

Таблицы и поля определяются по роли и подписям, без фиксированных номеров таблиц/строк и глобального поиска по плоскому тексту. Поддержаны пустые ячейки оформления, перестановка таблиц и пар полей, значение в соседней ячейке или после подписи в той же ячейке. Colspan/rowspan ячеек оформления не сдвигают поиск: подпись и значение связываются внутри одной строки, сетка через несколько строк не достраивается по догадке. Вложенная таблица читается самостоятельно, её текст не входит в значение внешней ячейки. `br`, `p`, `div` сохраняют логические границы текста.

Название детали, даже начинающееся с «Материал», «Спецификация №» или содержащее `Вес`, `кг`, `.rcam`, не читается как итоговое поле. Результаты не привязаны к расширению имени заказа внутри заголовка. Отдельный профиль не заменяет распознавание всех возможных версий отчёта: если структура/метки неизвестны, нужны диагностика и дополнительный образец.

## Неоднозначности и источники

`SpecificationParseResult` содержит значения и `SpecificationIssue` с полем, стабильным кодом и уровнем. Каждый распознанный факт имеет ссылки на таблицу, строку, ячейку (индексы с нуля), подпись и исходный текст. Некорректные/разные значения сохраняют источники в диагностике; первый подходящий кандидат не выбирается молча. Одинаковые повторные значения допустимы, все источники сохраняются.

Обязательные пропуски, неверные числа, разные материалы/итоги, несколько разных заголовков и противоречие толщины блокируют нормализацию. Ноль не заменяет неизвестное значение; количество деталей/листов должно быть положительным. Не выполняется подмена итоговых пробивок суммой деталей: в предоставленных ранее документах они различаются, причина ещё не подтверждена.

`SheetLayouts` сохраняет все размеры, количества по вариантам (если указаны) и исходные ячейки. `Dimensions` заполнено только при одном уникальном наборе габаритов. По решению пользователя несколько размеров **одной толщины** допустимы в одной заявке: `Размер_листа` получает, например, `1000x2000, 1250x2500`, `Кол_во_листов` — общий итог; длина, вес, детали и пробивки также остаются итоговыми. Повторные размеры перечисляются один раз в порядке документа, их источники не теряются. Запись не разбивается автоматически и не получает новых множителей цены.

Список размеров ограничен 255 символами существующего `Text(255)`; превышение даёт `SheetSizeTooLong`, без усечения. Разные толщины дают `ConflictingThickness`: в прежней MDB одна толщина на заявку. Если у всех уникальных вариантов явно указаны количества, их сумма сверяется с итогом (`SheetCountMismatch`). При неполных количествах или повторных наборах не придумывается распределение. Старый код загружает размер в редактируемое текстовое поле и выводит строкой, не разбирая его для расчёта. Это проверка схемы и исходного кода; открытие такой записи старым EXE в общей папке остаётся ручной Windows-проверкой.

Длительность необязательна: её отсутствие/ошибка видны как предупреждение, но не уничтожают достоверно распознанные поля MDB. С 17.10.2026 сохраняется отдельно от Orders по [контракту времени](cutting-time.md). Начальные признаки `@`/`*@` оставляют документ вне HTML-профиля БЛОК; будущий HansLaser-профиль должен сохранить их смысл. Префикс, который добавлял старый файловый загрузчик, не внедряется в новые документы.

## Нормализация и расчёт

Сохраняется прежнее правило длины БЛОК: `truncate(мм) / 1000` с целочисленным делением, затем `+ 1`. Для **1000 мм результат 2 м**, это намеренно отличается от `Ceiling`. Нормализатор этого профиля не применяется к HansLaser. Явная подпись метров `(м)` переводится в миллиметры до того же правила; неизвестные единицы не угадываются.

Коэффициент рассчитывается общим `CuttingPriceCalculator.CalculatePunchCoefficient` по **итоговым** деталям и пробивкам, с прежними Double/ToEven и шкалой. Цена здесь не читается и не вычисляется, количество листов не добавляется как новый множитель. Нормализованные размеры, количество листов и вес выводятся числами invariant culture; исходные значения остаются в источниках. Старые строки базы не нормализуются и не пересчитываются.

## Диагностика

```bash
./scripts/dotnet.sh run --project tools/Jornal.Inspect -- \
  block-spec "/путь/спецификация.html" "/путь/другая.htm"
```

Для каждого файла выводится JSON: отчёт/источники/сообщения и нормализованная заявка при полном распознавании. Команда ничего не пишет в MDB или спецификации. Код завершения 1 означает хотя бы один отказ/неполный разбор; остальные переданные файлы всё равно обрабатываются. JSON с реальными значениями сохранять только в `.local/`/закрытую папку, не публиковать вместе с кодом.

## Проверки и дальнейшие шаги

Публичные тесты используют вымышленные документы: долгие и служебные имена, одинарный/двойной дефис, другие расширения, разные материалы, длительность > суток/недели, несколько размеров, расхождение количеств/толщин, лимит 255 символов, вложенные таблицы, незакрытые строки, переносы/пробелы, неоднозначности, отсутствие итогов, неизвестные форматы/маркеры, исходные ячейки и прежнее округление. Нативная проверка создания заявки в Windows сверяет сохранение/повторное чтение списка размеров через Jet, остальные поля и неизменность схемы.

Для частного корпуса есть `JOURNAL_BLOCK_SPEC_MANIFEST`: путь к JSON-массиву `{Id, Path, Expected}`, где Expected — `NormalizedBlockSpecification`, значения предварительно сверены по документу отдельно от нового парсера. Дополнительные `Layouts` и `Raw` проверяют все габариты/количества, исходные итоговые числа и длительность. Для неполного разбора можно задать `Expected: null` и `ExpectedErrors`. Опциональный тест сравнивает поля и хеш каждого исходного файла до/после. Корпус и ожидания с реальными данными в Git не входят.

Все 29 сверены с отдельно прочитанными ячейками и независимыми ожиданиями. Вместе с двумя дополнительно найденными старыми отчётами частный корпус содержит 31 файл. Первоначальные семь HTML по старым путям пока не перепроверены; это также не прогон старого EXE на Windows. Просмотр импорта в форме с ручной проверкой подключён следующим этапом ниже; отдельные PDF/текстовый профиль и расширение корпуса остаются дальнейшими шагами. Автоматическое обновление существующей заявки по совпадению номера пока не реализовано. Пакетное создание добавлено позднее по [UX-42](batch-import.md).

## Импорт в форму и перетаскивание

Следующий этап подключает профиль к приложению. Перетаскивание одного HTML/HTM на главное окно показывает оверлей; после отпускания документ читается в фоне, доступны «Отменить разбор» и Escape. Закрытие окна отменяет чтение, запоздалый результат не открывает форму. Повторное перетаскивание не запускает второй разбор. На время чтения недоступны запись, смена источника и применение обновления. Текстовые перетаскивания не перехватываются. Несколько файлов открывают пакетное окно; неподходящие элементы остаются карточками с причиной, первый файл не выбирается молча. См. [пакетный импорт](batch-import.md). Для одного PDF используется отдельный HansLaser-профиль, а не этот HTML-парсер.

После успешного распознавания открывается обычная «Новая заявка»: достоверные поля подставлены, отсутствующие/противоречивые пусты, без даты по умолчанию, станка или коэффициента 1. Показаны файл, длительность, детали/пробивки и сообщения с исходными вариантами. Под полями — признак импорта/ручной правки и подсказка с исходной ячейкой. При замечаниях предупреждение видно в шапке формы, подробности прокручиваются справа. Исходный HTML не выполняется и не показывается как веб-страница. Менеджер/заказчик заполняются вручную. Поля можно исправлять; перед сохранением действует обычная валидация и расчёт, автоматического INSERT/поиска дубля по номеру нет.

«Выбрать спецификацию» в форме выбирает HTML/PDF; HTML использует тот же профиль, PDF — отдельный HansLaser-профиль. Для заполненных параметров сначала требуется явное «Заменить параметры» или «Оставить прежние», менеджер/заказчик сохраняются. Ошибка чтения и отмена не стирают прежний ввод/расчёт. Неизвестный исход предыдущего добавления и сохранённая до F5 форма блокируют новый импорт, чтобы не потерять ввод и не замаскировать возможную запись.

Распознанные общие детали/пробивки передаются необязательными `PartCount`/`PunchCount` в прежние сегменты `Коэффициент`: `коэффициент|детали|пробивки|ID|газ`. При ручном вводе/неизвестных значениях сохраняется прежний `-1`; новых полей MDB нет. Пользовательский коэффициент можно изменить, сами исходные количества от этого не подменяются. Длительность заполняет редактируемое ЧЧ:ММ с округлением секунд вверх; сохраняется отдельно от Orders по [контракту времени](cutting-time.md). Windows использует существующие транзакции/хост x86; Linux — редактируемую локальную копию, исходная MDB остаётся read-only.

Сценарии проверяются настоящими routed drag/drop-событиями Avalonia Headless, включая отмену/повтор, обе темы, компактную форму, длинное имя и частичный разбор. Частный корпус дополнительно проверяет заполнение формы без записи. Нативные тесты Windows проверяют сохранение размеров и сегментов количества через Jet и установленный хост. Перетаскивание из Проводника/файлового менеджера и реальная общая папка остаются ручной проверкой; headless не заменяет интеграцию DnD операционной системы. PDF HansLaser подключён следующим этапом по отдельному контракту. Вставка текста/редактор правил ещё не подключены. Пакетный импорт и последовательное добавление реализованы по [отдельному контракту](batch-import.md).

Итог проверки распознавания 17.10.2026: полный `scripts/check.sh` — 678 проверок пройдены, 14 частных/платформенных пропущены, 40 нативных Access-тестов пропущены на Linux; сборка без предупреждений/ошибок, 11 release-проверок успешны. Корпус 29 HTML + 60 PDF проверен с SHA-256 до/после без изменений. Снимки приёма/запрета/ошибки в обеих темах просмотрены. Настоящий DnD из Проводника Windows и с общей папкой требует отдельного ручного прогона.


## Пакетное окно · UX-42

При нескольких файлах или добавлении второго перетаскиванием — общая шапка менеджера/заказчика и карточки спецификаций; прежняя одиночная форма сохраняется для первого файла. Смешанный набор обрабатывается поэлементно, ошибочные включённые карточки блокируют запись. Сохранение выбранных — одной транзакцией, каждая карточка отдельной строкой Orders. Никакого молчаливого пропуска, автоматического INSERT или повтора неизвестного commit. Детали переходов, границы и проверки — [пакетный импорт](batch-import.md).


В редакторе одной существующей заявки импорт заменяет её параметры с подтверждением, включая переход HTML ↔ PDF/смену станка, без создания нового ID. Diff справа, NULL/неприменимые параметры и сохранение — [замена спецификации](order-maintenance.md#замена-спецификации-в-редакторе--ux-43-17102026), UX-43.
