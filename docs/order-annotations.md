# Гибка и комментарий

Расширение от 23.10.2026: [фаска и дополнительные операции](order-operations.md)
хранятся отдельно. Состав и формат описанной ниже таблицы не меняются.

Локальная реализация 18.10.2026, ещё не опубликована. Это ручные свойства каждой заявки: необязательная гибка и комментарий до 255 символов. Комментарий допускает переносы строк; управляющие символы, кроме CR/LF/табуляции, отклоняются. Они не меняют расчёт цены.

В таблице «Гибка» показывает ✓, а «Комментарий» — одну строку с обрезкой и полной подсказкой. Оба столбца доступны в настройках таблицы, их порядок/ширина/видимость сохраняются. Редактирование только в формах: «Гибка» после всех параметров станка, непосредственно перед комментарием, с выравниванием по левому краю полей ввода. Общий компонент используется в создании, редактировании и карточках пакета. У комментария счётчик длины. Крестик внутри непустого поля очищает только ввод, возвращает фокус в поле; запись меняется после сохранения. Редактор показывает изменения обоих свойств в правой панели. Для пакетного импорта значения отдельные у каждой карточки; переход из заполненной одиночной формы сохраняет её пометки только у первой карточки. Замена спецификации оставляет ручные пометки.

«Задание на резку» добавляет ` ГИБКА` после толщины и материала только соответствующей заявки. Сортировка по толщине внутри станка и группировка остаются прежними. По уточнению от 23.10.2026 результат для письма добавляет `   ГИБКА` и/или `   ФАСКА` в конце соответствующей строки после названия станка. Текст комментария не включается в задание, результат письма или «Комментарий строки».

## MDB и обратная совместимость

По уточнению пользователя разрешена **отдельная необязательная** таблица `JournalOrderAnnotations` в прежней MDB. Все 16 полей `Orders`, прайсы, ключи, коэффициент и четырёхколоночная `JournalOrderExtras` остаются прежними. Новые обязательные поля, внешние ключи, каскады и ограничения на `Orders` не добавляются. Старый EXE продолжает использовать прежние SQL и игнорировать пометки.

| Поле | Тип Jet | Назначение |
| --- | --- | --- |
| OrderId | LONG, PK | Исходный Orders.Код |
| HasBending | BIT NOT NULL | Ручная гибка |
| Comment | TEXT(255), NULL допустим | Ручной комментарий; пустой текст записывается как SQL NULL |
| IdentityHash | TEXT(64) NOT NULL | SHA-256 даты и номера спецификации, версия привязки |
| FormatVersion | SHORT NOT NULL | Формат записи: 1 |

Нет строки пометок — нет гибки и комментария. Снятие гибки и очистка комментария удаляют дополнительную строку. Ошибку чтения нельзя подменять отсутствием пометок: исходный журнал остаётся доступным, таблица показывает `?` / «Проверить» и подсказку; формирование задания для таких строк блокируется до успешного чтения. Полное редактирование/удаление требуют полного снимка, поэтому при неизвестной структуре пометок они не продолжаются вслепую.

### Первое подключение

Только рабочий Windows-источник UI готовит таблицу автоматически. Сначала читает исходный список, затем независимо готовит время и пометки. При уже существующей таблице проверяет её структуру и ничего не добавляет. Если таблицы нет:

1. Проверяет исходные 16 столбцов `Orders`.
2. Сохраняет рядом полную копию `*.before-journal-annotations-<UTC>-<GUID>.bak`, с эксклюзивным файловым доступом и сбросом на диск.
3. Открывает MDB через исключительный Jet, повторно проверяет наличие таблицы и создаёт только `JournalOrderAnnotations`.

Занятая база, недостаточные права или ошибка резервной копии дают предупреждение; исходный журнал не скрывается. Для первой подготовки общей MDB нужно закрыть остальных клиентов и повторить F5. Успешные подготовки не повторяются при каждом F5; неудавшаяся повторяется. Неизвестная существующая структура не заменяется. Если значения пометок действительно заданы, перед записью также требуется успешная подготовка; отказ не сохраняет заявку частично. Читающие CLI и Linux не выполняют DDL. Резервные копии автоматически не удаляются.

### Конфликты, старая программа и корзина

Создание, изменение, удаление и восстановление пометок входят в ту же Jet-транзакцию, что и `Orders` / время. Полный снимок содержит пометки: чужое изменение только комментария или флага также вызывает конфликт. Условные UPDATE/DELETE проверяют исходные значения, включая бинарное сравнение текста. При ошибке до commit выполняется rollback; неизвестный исход commit требует F5, повторная запись автоматически не выполняется.

Цвет/статус, БЛЦБ и обычные изменения менеджера/параметров сохраняют пометки. Привязка учитывает дату (без времени суток) и номер спецификации. Смена станка, материала или веса не стирает ручные свойства. При изменении номера/даты прежние пометки требуют ручной проверки в редакторе; до подтверждения ✓ и комментарий не показываются как актуальные и задание не копируется. Изменение номера при замене спецификации также показывает краткое подтверждение.

Старый EXE не умеет обновлять/удалять пометки. Его DELETE может оставить дополнительную строку без заявки. Она не показывается и автоматически не уничтожается. Если тот же ID занят/имеет оставшиеся пометки, восстановление не перезаписывает их: транзакция отменяется, архив остаётся. Привязка не способна отличить удалённую и заново созданную старым EXE запись с **тем же ID, датой и номером** — это известное ограничение старой схемы без неизменяемого UUID. Не добавлять ради него ограничения на старые Orders.

Локальная корзина хранит полный `OrderRecord` вместе с пометками и временем. Восстановление возвращает исходные значения/ID/цену, а не пересчитывает их. Архив остаётся вне MDB.

## AccessHost, Linux и проверки

Протокол остаётся 1, прежние номера операций сохранены. Добавлена `PrepareAnnotations = 15`, ответ с `AnnotationsPrepared=true`; текущий хост всегда сообщает `AnnotationsSupported=true`. Старый хост без этой возможности не может подтвердить подготовку или полноту записи: клиент отмечает пометки недоступными и не отправляет запись с заданными пометками без подготовки. Клиент сверяет полный ответ создания/изменения/восстановления с запросом, включая пометки. Нужна согласованная поставка Desktop и AccessHost.

В Linux исходная MDB по-прежнему только для чтения: MDB Tools читает необязательную таблицу, различая SQL NULL и текст `NULL`. Рабочая `.journal-test.json` сохраняет новое необязательное свойство `Annotations` в списке и полных снимках; старые JSON без свойства читаются. Обратной записи в MDB и обещания совместимости нового JSON со старым v2 нет.

Проверки: `OrderAnnotationsTests`, `OrderAnnotationsWindowTests`, `MaintenanceProtocolTests` проверяют валидацию, задания, формы/темы, пакетный импорт, JSON, конфликты, корзину и защиту протокола. `NativeOrderAnnotationsTests` и расширенный тест упакованного AccessHost предназначены для Windows Jet x86: подготовка/копия, занятая база, прежняя схема, строки с NULL/кавычками/переносами/255 символами, транзакции и старые SQL. На Linux они не выполняются и не доказывают совместимость Jet.

Перед публикацией обязательны Windows Jet/упакованный хост, затем ручной прогон **на копии** MDB старым EXE и по общей папке. Рабочая пользовательская MDB при разработке не изменялась. Текущий локальный этап — без push/PR/релиза.

Локальная проверка 18.10.2026: `scripts/check.sh` — 20 проверок выпуска, Release-сборка без предупреждений, 873 теста общего контура прошли (16 зависят от отсутствующего окружения); все 63 Windows-native проверки пропущены на Linux. После добавления крестика и сохранения за одно нажатие повторены Release-сборка и 49 затронутых проверок — успешно. Просмотрены снимки форм/таблицы в обеих темах. Это не нативная проверка MDB.
