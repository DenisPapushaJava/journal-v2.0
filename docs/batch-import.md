# Одиночный и пакетный импорт спецификаций

Реализовано локально 17.10.2026, UX-42. Публикация не выполнялась. Форматы/распознавание — [общий контракт](specification-import.md), цена — [расчёт](pricing.md), длительность — [время резки](cutting-time.md).

## Пользовательский сценарий

- Один файл на главном экране сохраняет прежнюю форму одной заявки. Файл можно также перетащить прямо в открытую пустую «Новую заявку».
- Второй файл, перетащенный в заполненную форму, переводит её в пакет; последующие добавляются карточками. Предыдущие поля, импортированные детали/пробивки, просмотренная цена и ручные правки сохраняются. Общие менеджер и заказчик остаются в шапке.
- Несколько файлов на главном экране сразу открывают пакетное окно, не дожидаясь чтения всех файлов. В новой заявке можно выбрать несколько файлов кнопкой папки. Один файл из этого диалога в одиночном режиме сохраняет прежнее подтверждение замены параметров; перетаскивание означает добавление. В пакетном режиме оба способа добавляют карточки.
- Карточка сразу показывает имя и состояние. Порядковый номер — отдельный компактный бейдж «№ 1» перед неизменным именем файла, чтобы не сливаться с толщиной в начале названия; после удаления карточки номера пересчитываются. После распознавания — свои дату/номер и редактируемые параметры резки. Ошибочный файл остаётся карточкой с причиной без выдуманных параметров. Достоверные поля неполной известной спецификации доступны для исправления.
- Каждая карточка включена в пакет по умолчанию. При ошибке/чтении включённой карточки сохранение недоступно: исправить поля, снять её галочку или убрать файл. Ничего не пропускается молча. Необязательные нераспознанные поля, например время, не запрещают сохранение.
- Пока идёт разбор, можно вводить общие данные, редактировать готовые карточки и добавлять/убирать файлы. Отмена чтения и закрытие окна отменяют ожидание; удалённая карточка не возвращается поздним результатом.
- Общий счётчик показывает готовые/включённые карточки; кнопка — число добавляемых заявок. После сохранения все созданные записи выделяются в журнале, черновик письма не заменяется.

Файлы последовательно по одному также образуют пакет: `1 → одиночная`, `2 → пакет из двух`, `3 → пакет из трёх`. Обратного автоматического переключения при удалении карточек нет. Для этого этапа принят предел 100 карточек, включая сохранённую текущую заявку; превышение отклоняется целиком без обрезания. Поиск одинакового пути учитывает регистр Windows; повтор остаётся ошибочной карточкой. Совпадающие дата/номер/станок в пакете и дата/номер/станок/заказчик в загруженном журнале дают предупреждение. Это не уникальный бизнес-ключ и не надёжный поиск дублей при одновременной работе разных клиентов.

## Приём и чтение

DragOver проверяет только метаданные и доступность операции, без чтения файлов/общей папки. Нейтральный оверлей без текста и красный запрет остаются общими. В смешанном наборе достаточно одного поддерживаемого расширения для приёма; каждый остальной элемент проверяется отдельно. Если подходящих расширений нет, весь набор получает запрет. Одно неверное расширение по-прежнему отклоняется до чтения.

`NewOrderViewModel` содержит одиночную форму и пакетные `BatchSpecificationItem` с теми же полями/валидацией/расчётом. `OrderParametersControl` переиспользует поля карточек. Один внешний прокручиваемый список с виртуализацией, общая шапка и нижние команды закреплены. Файлы разбирает общий `ISpecificationImportService`, одновременно не более двух. Новые профили подключаются через каталог, без отдельного пакетного парсера. Прежние ограничения размера/страниц, отмена, источники и безопасная диагностика действуют на каждый файл. Документы ничего не исполняют и автоматически не записываются.

Параметры/превью живут в памяти формы; закрытие не создаёт новых черновиков на диске. После неизвестного исхода записи сохраняется вся форма по прежнему механизму F5, без автоматического повтора. Это не обещает восстановление пакета после аварийного завершения приложения.

## Атомарное сохранение

Уточнение 18.10.2026: отсутствие тарифа — ошибка проверки цены, а не готовая карточка. Сразу под шапкой карточки видны станок, толщина и предложение заполнить «Прайсы», статус — «Проверьте цену». После обнаружения ошибки «Добавить» недоступно; «Рассчитать» остаётся доступным для исправленного прайса. Изменение параметров цены также снимает устаревшую причину, при следующем действии тариф проверяется заново. Технические ошибки чтения прайса сохраняют ввод и допускают повторный расчёт или повторную проверку кнопкой добавления; запись до успешной проверки не вызывается. Блокировка модуля Windows и прежняя помощь по её устранению сохраняются.

При добавлении без предварительного расчёта проверяются все включённые карточки до вызова записи. Общая строка показывает номера карточек с ошибками (до пяти и число остальных). Весь пакет остаётся несохранённым. Исправление с повторным расчётом, явное исключение или удаление проблемных карточек очищает только это уведомление; другие технические ошибки и неизвестный исход записи не скрываются. Автоматического добавления после исправления нет.

`IManualOrderBatchCreator.CreateBatchAsync` принимает снимок 1–100 `ManualOrderDraft`. Каждый файл создаёт отдельную строку `Orders` с общими менеджером/заказчиком и своими параметрами. Схема/16 полей/типы/сегменты коэффициента прежние. Для времени используется уже разрешённая необязательная `JournalOrderExtras`, не новое расширение ради пакета.

Windows: один запрос `CreateOrders = 11` протокола AccessHost 1 (значения 0–10 сохранены, новые поля необязательные) → `OleDbManualOrderCreator`. Валидация всех черновиков и подготовка хранения времени до транзакции; парсинг и ожидание пользователя завершены заранее. В одной короткой транзакции читаются нужные прайсы, сверяются просмотренные цены всех заявок, затем выполняются типизированные INSERT, получение каждого AutoNumber, запись времени и read-back. Один commit. Сбой до commit с успешным rollback не сохраняет ни одной заявки; сбой commit/rollback или повреждённый ответ после отправки — `OutcomeUnknown`, запрет повторной записи и успешный F5 перед ручным решением. После commit MDB повторно не читается.

Изменившийся прайс возвращает индекс карточки и проверенную новую цену; весь пакет не добавлен, требуется повторное явное сохранение. Клиент подтверждает число строк, уникальные положительные ID, поля/время и просмотренную цену каждой записи. Нет последовательного цикла независимых `CreateAsync`, автоматических повторов, объединения по номеру или перезаписи существующих заявок. AutoNumber может иметь пропуски после rollback — это нормальная работа Access.

Linux `LocalJournalStore`: один lock, подготовка всех строк и атомарная замена одного JSON, прежние данные/прайсы сохраняются. Исходная MDB read-only. `DemoOrderStore`: весь пакет в памяти под одной блокировкой, без выдуманной цены. Не поддерживающий пакет источник сообщает об этом явно.

## Проверки и границы

Проверки отказа цены 18.10.2026: отсутствующая колонка и NULL, добавление с расчётом и без него, отсутствие `PriceCalculationException` даже на уровне FirstChance в обычном сценарии, побайтовая неизменность Linux-копии при отказе, сохранение полей/гибки/комментария, исправление прайса и повторный расчёт, явное исключение карточки, настоящий нулевой тариф. Проверены недоступное чтение и повторная попытка, чтение одного прайса/каталога один раз за проверку, изменение/удаление тарифа после проверки UI с отказом окончательной записи. Обе темы окна проверены в 1060×660: причина сразу под шапкой карточки, общая строка и действия видимы. Это локальные проверки Linux; отдельный нативный Jet, старый EXE и SMB ими не подтверждаются.

Проверяются смешанный набор, частичный импорт/ручное исправление, общая шапка, последовательные добавления, сохранение прежнего ввода, повтор файла, предел, ограничение параллелизма, отмена/поздний результат, F5 после неизвестного commit и отсутствие автоповтора. Linux-копия проверяет атомарность, изменившийся тариф, пропавший прайс, уникальность ID при конкуренции и неизменность файла при отказе. Искусственный процесс проверяет ответы AccessHost, включая повреждённые/неполные ответы и индекс цены. Routed DnD и окно проверяются в обеих темах, 1240×760/1060×600.

Отдельный Windows-контур Jet проверяет атомарный пакет, ошибку второго INSERT, rollback времени вместе с Orders, сохранение старых полей/схемы/прайсов. Проверка упакованного x86-хоста расширена успешным пакетом и отказом при устаревшей цене. На Linux этот контур пропущен: компиляция и искусственный хост не доказывают работу Jet. Старый EXE, Explorer DnD, SAC, офлайн-установка и настоящая SMB-папка остаются отдельными полевыми проверками на копии.

Уточнение пользователя 17.10.2026: обычный пакет содержит спецификации с одной датой, поэтому при сортировке по дате записи ожидаются рядом. Разные даты допустимы: дата каждой заявки берётся из её внутреннего заголовка, не подменяется общей датой пакета/текущей датой/именем внешнего файла.

Источник номера и даты повторно подтверждён пользователем: внутренний заголовок/идентификатор заказа, дата формирования документа может быть любой. Ошибка его разбора оставляет поле пустым для ручной проверки. Это же правило сохраняется в каждой карточке пакета.

Итог локальной проверки 17.10.2026: `scripts/check.sh` успешно — 704 проверки пройдены, 14 частных/платформенных пропущены; 44 нативные Access-проверки пропущены на Linux. Сборки Debug/Release без предупреждений/ошибок, 11 release-проверок успешны. Включён частный корпус 89 файлов с SHA-256 до/после без изменений; обе темы/компактное окно просмотрены по итоговым снимкам. Нативный Windows/Jet/старый EXE/SMB этим не проверены. Навыки проходят quick_validate.py, `git diff --check` чистый. Без push/PR/релиза.

Исправление 18.10.2026: при обновлении привязок TextBox/ComboBox в поле карточки может прийти null. Ранее это воспроизводило NullReferenceException в Validate на Trim. Ввод OrderEntryField.Value и комментария нормализует null в пустой текст **до** PropertyChanged, сохраняя сообщения валидации/импорта и проверку заполнения. Сохранение неполной карточки блокируется, соседние карточки не меняются; после исправления поля весь пакет сохраняется. UI-тесты проверяют настоящие двухсторонние привязки в обеих темах и сохранение выбора при обновлении каталога. Сырые NULL MDB/парсер/расчёты не менялись; рабочая база не использовалась.

Проверка исправления 18.10.2026: до правки регрессионный тест воспроизвёл тот же стек (Validate:221 → ValidateBatchParameters → BatchSpecificationItem → сеттер Value). После правки три проверки null/привязок прошли; scripts/check.sh — 20 release-проверок, сборка без предупреждений, 876 общих тестов пройдены/16 пропущены по окружению. 63 Windows-native теста пропущены на Linux. Дополнительно обе темы проверены с повторным обновлением каталога станков; рабочая MDB не менялась. Без push/PR/релиза.
