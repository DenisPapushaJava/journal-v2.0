# Создание заявки с расчётом и сохранением в MDB

На Windows «Новая заявка» подключена к существующей MDB. В Linux-копии используется та же форма и общий расчёт, а запись остаётся в локальном JSON. Схема MDB не меняется; исторические строки не переписываются.

## Сценарий

1. Подключить отдельную тестовую копию MDB через «База данных».
2. Заполнить дату, номер, менеджера/заказчика, параметры резки, материал, вес/листы и коэффициент. Произвольные материалы без пробелов допустимы. Количество листов — одно число, например `3`, `1,3` или `1.3`; при ручном вводе допустимы ноль и знак. Выражения `2+1`, перечни и слова не сохраняются. Импорт HTML отдельно проверяет целый положительный итог; вручную его можно изменить.
3. Толщина выбирается из доступных тарифов станка, без свободного ввода. Неподдерживаемая толщина из спецификации остаётся видна с ошибкой; из поля можно открыть нужный прайс и вернуться к тому же вводу. Правила, обновление и отказы — [pricing.md, UX-51](pricing.md#выбор-толщины-в-заявке--18102026-ux-51).
4. «Рассчитать» показывает сумму и расшифровку «тариф × целые метры × коэффициент». Изменение параметров цены сбрасывает расчёт; исправление имени заказчика его не сбрасывает.
5. «Добавить заявку» читает актуальный прайс и сохраняет запись. Предварительная кнопка необязательна: без неё цена вычисляется при добавлении. Если просмотренный тариф изменился, сохранение останавливается, показывается новая цена; после проверки пользователь нажимает добавление ещё раз.
6. Новая запись появляется выбранной в журнале, прежние фильтры сбрасываются для её видимости. Подготовленный результат для письма сохраняется.

Отсутствующие/NULL тарифы и неверные параметры не создают заявку с нулём вместо цены. Настоящий нулевой тариф допустим. Формула, диапазоны и выбор прайса — [pricing.md](pricing.md).

## Совместимость и надёжность

Windows-комплект использует свой AccessHost x86 к системному Jet. В разработке без хоста применяется OLE DB текущей разрядности. Новая операция `CreateOrder` добавлена в конец enum протокола 1; прежние значения сохранены.

`OleDbManualOrderCreator` проверяет ввод, затем в одной транзакции читает выбранный прайс, выполняет INSERT с типизированными позиционными параметрами и получает AutoNumber через отдельный `SELECT @@IDENTITY` на том же соединении. Сохранённая строка читается и сверяется до commit; после успешного commit запросов к MDB нет. [Позиционные параметры OLE DB](https://learn.microsoft.com/en-us/dotnet/api/system.data.oledb.oledbcommand.parameters), [AutoNumber Jet](https://learn.microsoft.com/en-us/dotnet/framework/data/adonet/retrieving-identity-or-autonumber-values#retrieving-microsoft-access-autonumber-values).

Сохраняются прежние типы: DateTime, Currency, Double, Long Integer, Unicode Text(255). БЛЦБ новой записи — NULL; коэффициент — `коэффициент|детали|пробивки|ID|газ`; ручной ввод без этих количеств сохраняет прежние `-1|-1`, импорт HTML передаёт распознанные итоговые количества. Отсутствующие ID/газ обозначены `-1`. Дата вводится без времени. Неизвестные детали/пробивки не подменяются нулём. ID выделяет MDB, не клиентский `MAX + 1`; номер спецификации не объявляется уникальным.

`InitialColor` берётся из локальной настройки «Общие → Цвет новых заявок» (UX-44, docs/settings.md), при отключении используется `-1`; в пакете одинаковый снимок цвета на все строки. Код `TechnologColor` можно вставить вручную, автоматический перенос старого конфига/подсказок менеджеров/заказчиков остаётся отдельным этапом. Работающий Office и Jet DLL установщик не меняет.

Подтверждённый отказ оставляет форму доступной для повтора с тем же вводом. Ошибка commit/rollback или обрыв поставляемого хоста после отправки записи означают неподтверждённый результат: запись могла сохраниться. Автоматического повтора нет. Сохранение блокируется; нужно закрыть форму, выполнить успешный F5 и проверить список. «Новая заявка» восстановит прежний ввод с предупреждением. Это сохранение в памяти текущего сеанса, а не восстановление после завершения процесса. После возобновления «Отмена» позволяет отказаться от прежнего ввода. F5 сам по себе не доказывает, что повтор не создаст дубликат: запись необходимо проверить.

На время добавления запрещены операции журнала и закрытие главного окна. Ошибка обновления экрана после commit не должна приводить к повторной записи. При предварительном расчёте форму можно закрыть, запрос отменяется.

## Проверка на Windows

Перед рабочей эксплуатацией выполнить на копии MDB:

- создать заявку с кавычками/кириллицей и дробной толщиной, проверить цену, ID, вес/листы и коэффициент после F5;
- открыть эту копию старой программой и проверить новую строку;
- проверить два клиента общей папки, блокировки и временную потерю связи; после неподтверждённого добавления искать уже сохранённую строку перед повтором.

Нативные тесты Windows используют искусственные MDB: все виды резки/ID, NULL/ноль/отсутствующий прайс, изменение тарифа, AutoNumber двух клиентов, откат после ограничения, неизменность старых строк и схемы. Установленный x64 → x86 хост проходит отдельную проверку создания. Эти проверки не заменяют ручной прогон старого EXE и SMB.

Редактирование и удаление с локальной корзиной описаны в [order-maintenance.md](order-maintenance.md). Импорт спецификаций и остальные функции переносятся следующими этапами. В Linux остаётся отдельная тестовая копия без обратной записи в MDB.


Пакетное создание реализовано отдельным `IManualOrderBatchCreator`, все выбранные черновики в одной транзакции; прежний одиночный метод сохранён. Контракт, индексы изменившихся цен и проверки — [пакетный импорт](batch-import.md).
