# Версии и выпуски Journal

Репозиторий: `DenisPapushaJava/journal-v2.0`. Название репозитория не задаёт номер версии приложения.

Сообщения новых коммитов, названия и описания PR, описание репозитория и заметки к выпускам пишутся на русском языке. Черновик получает русский шаблон из `docs/release-notes.md`; перед публикацией его дополняют конкретными изменениями выпуска.

## Версия

Принята Calendar Versioning (CalVer), схема **ГОД.ВЫПУСК.ИСПРАВЛЕНИЕ**:

- `2026.1.0` — первый выпуск 2026 года.
- `2026.1.1` — исправление в этой линии выпуска.
- `2026.2.0` — следующий выпуск с новым набором изменений.
- `2026.1.0-alpha.1`, `-beta.1`, `-rc.1` — предварительные выпуски.

Вторая часть — последовательный номер выпуска, не неделя и не месяц. В новом году нумерация начинается с 1. Тег содержит префикс `v`, например `v2026.1.0-alpha.1`. Всегда используются три числовые части без ведущих нулей. `.NET AssemblyVersion/FileVersion` получают `2026.1.0.0`; полная версия с суффиксом и ревизией Git остаётся в метаданных сборки. Локальная версия по умолчанию — `2026.1.0-dev` в `Directory.Build.props`; версия тега переопределяет её при выпуске.

## Минимальные процессы

**CI:** push в `main`, pull request или ручной запуск → восстановление закреплённых зависимостей → Release-сборка → тесты на Linux и Windows. Результаты тестов доступны 7 дней. Проверяется только новое решение `Jornal.Modern.slnx`; WinForms не входит в эту сборку.

**Release:** push тега `v*` → проверка версии → сборка и тесты обеих платформ → ZIP для `win-x64` и `linux-x64`, Velopack Setup.exe/AppImage и пакеты обновлений → SHA-256 → **черновик** GitHub Release. Задания упаковки имеют права чтения; только задание создания черновика получает `contents: write`. Дополнительный PAT не нужен. Actions закреплены SHA.

Ручной запуск `Release` с полем `version` выполняет тот же процесс упаковки и сохраняет артефакты на 14 дней, но не создаёт тег или GitHub Release. Так можно проверить процесс заранее. Повторный запуск для существующего черновика обновляет его файлы; уже опубликованный релиз не перезаписывается.

## Выпуск

Изменения сначала попадают в `main` через короткую ветку и PR по [порядку разработки](development.md). После успешного CI для нужного коммита:

```bash
git switch main
git pull --ff-only origin main
git tag -a v2026.1.0-alpha.1 -m "Предварительный выпуск Journal 2026.1.0-alpha.1"
git push origin v2026.1.0-alpha.1
```

Проверить черновик, состав архивов, заметки и запуск на целевых ОС, затем опубликовать через GitHub Releases. Автоматического еженедельного выпуска нет. Опубликованные теги не передвигаются: для исправления выпускается новая версия.

Локальная проверка упаковки:

```bash
python3 -m unittest discover -s tests/release -v
python3 scripts/release.py validate --version 2026.1.0-alpha.1
python3 scripts/release.py package --version 2026.1.0-alpha.1 --runtime linux-x64 --updates
```

## Текущая граница поставки

Сейчас ZIP — framework-dependent предварительная сборка с деморежимом, чтением MDB и Windows-записью статусов/БЛЦБ: .NET 10 Runtime и драйвер Access в неё не входят. Для MDB на Windows нужен совместимый ACE текущей разрядности, на Linux — `mdbtools`. Это не выполнение требования об офлайн-установщике. Будущий Windows-установщик должен включать и проверять все необходимые компоненты, сохранять существующую MDB и настройки. Пока перенос создания/редактирования заявок, расчётов и установщик не готовы, сборки следует считать предварительными; текущие ограничения перечислены в `docs/release-notes.md` и внутри архивов.

Рабочая база, реальные спецификации, локальные профили и частные заметки не включаются в Git или ZIP. Исходный публичный WinForms-проект остаётся источником сравнения; новый репозиторий имеет собственную ветку `main` и независимые выпуски.

## Обновления из программы

Velopack NuGet и локальный CLI `vpk` закреплены на версии 1.2.0 (`Directory.Packages.props`, `.config/dotnet-tools.json`). Пакеты собираются на своей ОС с `--updates`: Windows Setup.exe и Linux AppImage, `.nupkg`, `releases.win-x64.json` / `releases.linux-x64.json`, служебные индексы и SHA-256. ZIP остаётся для разработки, обновление из него не применяется. AppImage framework-dependent: .NET 10 и mdbtools нужны отдельно. Setup может скачать .NET 10 при необходимости; это предварительный онлайн-установщик без ACE и не полный офлайн-пакет.

После публикации проверенного GitHub Release установленная программа находит его без GitHub-токена. По умолчанию используется стабильный `/releases/latest`, чтобы частые beta не вытесняли стабильный выпуск из первых десяти записей API. Явно выбранный тестовый канал включает prerelease, используя те же feed ОС/архитектуры; downgrade отключён. Перед публикацией нужно согласовать тег/версию пакета, флаг prerelease и описание в `docs/release-notes.md`. Не публиковать стабильный пакет под тестовым тегом или beta с флагом стабильного релиза. Пакеты и feed публикуются вместе; одного тега/ZIP недостаточно.

После загрузки журнала проверяются только метаданные, затем проверка повторяется раз в 6 часов, пока не найдена новая версия. Фоновых скачиваний нет. Ручная проверка сдвигает следующую фоновую на 6 часов; общий признак занятости не позволяет пересекать проверку, загрузку и установку. Фоновая ошибка сети/тайм-аут записывается только в диагностический Trace, без изменения видимой ошибки или всплывающих окон; повтор — через 6 часов. Срок запроса ограничен 30 секундами. Один отменяемый таймер использует монотонное время; после сна нет накопления пропущенных попыток. Закрытие главного окна отменяет цикл и ожидание запроса. Уже найденный/загруженный пакет фоновые проверки не заменяют.

Колокольчик открывает окно с изменениями. Пользователь отдельно скачивает пакет и запускает установку с перезапуском. Velopack проверяет размер/хеш пакета; автоматическое применение при старте отключено. Ошибка проверки не мешает журналу; при ручной проверке она объясняется в окне обновлений. Результат перед перезапуском атомарно сохраняется в `Journal/update-restart.json` вне приложения и однократно восстанавливается; при MDB того же пути восстанавливаются и ID добавленных в результат заявок. Путь к MDB и настройки уже хранятся отдельно от установки.

До запуска Update.exe должны закончиться чтение/запись MDB, копирование, настройка экрана и работа других форм. Для Windows проверяются другие процессы той же установки. MDB внутри заменяемой папки приложения блокирует обновление: файл автоматически не перемещается. Полный офлайн-установщик, автоматический подбор Access Runtime и ручная проверка на рабочих Windows 10/11 остаются отдельными задачами.

CI дополнительно собирает реальные установочные артефакты на обеих ОС и запускает `scripts/test-update-install.ps1` на Windows: изолированная тестовая программа использует настоящий адаптер обновлений, устанавливается в случайную временную папку, обновляется с `2026.1.0` до `2026.2.0` и пишет результат после перезапуска. Проверяются восстановленный текст и неизменность искусственных внешних данных/настроек; рабочая MDB не используется. Этот цикл выполнен в Windows CI. На Linux аналогичный цикл AppImage выполняет `python3 scripts/test-update-install-linux.py`; он также успешно выполнен локально. Это проверки механизма установки и перезапуска, а не публикация или испытание рабочей MDB.
