# Версии и выпуски Journal

Репозиторий: `DenisPapushaJava/journal-v2.0`. Название репозитория не задаёт номер версии приложения.

Сообщения новых коммитов, названия и описания PR, описание репозитория и заметки к выпускам пишутся на русском языке. Черновик получает русский шаблон из `docs/release-notes.md`; перед публикацией его дополняют конкретными изменениями выпуска.

## Краткое описание обновления

`docs/release-notes.md` одновременно используется в GitHub Release и канале
Velopack. Окно приложения показывает NotesMarkdown обычным TextBlock без
Markdown-рендера. По уточнению пользователя 19.10.2026 заметки пишутся простым
русским текстом для пользователя: только полезные ему изменения, обычно до
3–5 коротких пунктов с символом «•». Краткое резюме необязательно. Для небольшого
исправления достаточно одного пункта; не дополнять список ради объёма.
Описывать, что стало удобнее или какая проблема исправлена, без внутреннего
устройства программы и сложных технических терминов. При необходимости —
одна строка о совместимости. Без Markdown-заголовков, выделения
звёздочками, обратных кавычек, таблиц и технических подробностей. Версия уже
видна в заголовке окна. Инструкции установки и подробные ограничения остаются
в README и профильной документации. Название поля NotesMarkdown не означает,
что приложение умеет отрисовывать Markdown; проверять реальный текст в feed.

Для планируемой `2026.1.0-alpha.14` по уточнению пользователя 19.10.2026
в описание однократно включены полезные изменения из `alpha.13` вместе
с текущими изменениями. Подготовленный текст — `docs/release-notes.md`:
только пункты, без вводной строки; у настройки кнопок указан короткий путь
по интерфейсу со стрелками.
Механизм обновления сохраняется: окно показывает описание целевого выпуска,
история описаний и её загрузка не добавляются. Это разовое объединение,
а не правило накопления заметок для следующих версий.

Принята Calendar Versioning (CalVer), схема **ГОД.ВЫПУСК.ИСПРАВЛЕНИЕ**:

- `2026.1.0` — первый выпуск 2026 года.
- `2026.1.1` — исправление в этой линии выпуска.
- `2026.2.0` — следующий выпуск с новым набором изменений.
- `2026.1.0-alpha.1`, `-beta.1`, `-rc.1` — предварительные выпуски.

Вторая часть — последовательный номер выпуска, не неделя и не месяц. В новом году нумерация начинается с 1. Тег содержит префикс `v`, например `v2026.1.0-alpha.1`. Всегда используются три числовые части без ведущих нулей. `.NET AssemblyVersion/FileVersion` получают `2026.1.0.0`; полная версия с суффиксом и ревизией Git остаётся в метаданных сборки. Локальная версия по умолчанию — `2026.1.0-dev` в `Directory.Build.props`; версия тега переопределяет её при выпуске.

## Минимальные процессы

**CI:** push в `main`, pull request или ручной запуск → восстановление закреплённых зависимостей → Release-сборка → тесты на Linux и Windows. Результаты тестов доступны 7 дней. Проверяется только новое решение `Jornal.Modern.slnx`; WinForms не входит в эту сборку.

16.10.2026 согласован переход к одному PR на законченный этап и условным проверкам по характеру изменений. Полный цикл установщика/обновлений должен выполняться при связанных изменениях и перед выпуском; обычные правки не должны всегда пересобирать поставку. [Принятые правила и текущий статус](development.md#согласованное-разделение-ci). Условный CI реализован отдельным этапом 17.10.2026: [состав проверок и защита обязательных статусов](ci.md). Тег выпуска по-прежнему запускает полный цикл. После squash исходная ветка сохраняется как архив подробных коммитов; следующий этап начинается от `main`.

**Release:** push тега `v*` → проверка версии → сборка и тесты обеих платформ → проверка установки/перезапуска Windows, OfflineSetup и обязательных транзакций Jet x86 → полный установщик Windows и пакет обновления с индексом → SHA-256 → **черновик** GitHub Release. По уточнению пользователя 19.10.2026 автоматическая поставка Linux временно приостановлена; разработка и тесты Linux сохраняются. Задания упаковки имеют права чтения; только задание создания черновика получает `contents: write`. Дополнительный PAT не нужен. Actions закреплены SHA.

Ручной запуск `Release` с полем `version` выполняет тот же процесс упаковки и сохраняет артефакты на 14 дней, но не создаёт тег или GitHub Release. Так можно проверить процесс заранее. Повторный запуск для существующего черновика обновляет тот же набор файлов. Если в нём остались лишние файлы прежней схемы, выпуск останавливается для ручной проверки; автоматически они не удаляются. Уже опубликованный релиз не перезаписывается.

## Состав файлов выпуска

По решению пользователя 19.10.2026 следующие выпуски содержат четыре загружаемых файла:

| Файл | Назначение |
| --- | --- |
| `Journal-<версия>-win-x64-OfflineSetup.exe` | Единственный пользовательский установщик, со всеми зависимостями |
| `DenisPapusha.Journal-<версия>-win-x64-full.nupkg` | Пакет для обновления через колокольчик |
| `releases.win-x64.json` | Индекс версии, размера и хеша пакета, заметки к обновлению |
| `SHA256SUMS` | Общий SHA-256 для этих трёх файлов |

GitHub также автоматически показывает два архива исходного кода. Служебные `.nupkg` и JSON остаются публичными: установленный клиент скачивает их по прежним именам и каналу `win-x64`. Отдельный Setup создаётся только как вложение OfflineSetup; ZIP, portable, AppImage, старые индексы `RELEASES-*`, `assets.*.json` и отдельные `.sha256` не публикуются. Исторические выпуски не меняются. Пакеты Linux и ZIP без `--updates` можно по-прежнему собрать вручную.

Windows-упаковка использует свежую временную папку. Перед копированием проверяются обязательные файлы, версия/приложение/тип пакета в feed, его размер и SHA-256. `artifacts/release` должен быть пустым: старые результаты не смешиваются с новыми. До Velopack сохраняется проверка, что в publish нет MDB/ACCDB/файлов блокировки/PDB. Draft скачивает точный артефакт `package-win-x64`; Linux-сборка, тесты обеих ОС, Jet и установка/обновление Windows остаются обязательными.

## Выпуск

Изменения сначала попадают в `main` через короткую ветку и PR по [порядку разработки](development.md). После успешного CI для нужного коммита:

```bash
git switch main
git pull --ff-only origin main
git tag -a v2026.1.0-alpha.1 -m "Предварительный выпуск Journal 2026.1.0-alpha.1"
git push origin v2026.1.0-alpha.1
```

Проверить черновик, четыре файла, заметки и запуск на Windows, затем опубликовать через GitHub Releases. Автоматического еженедельного выпуска нет. Опубликованные теги не передвигаются: для исправления выпускается новая версия.

Проверка инструментов и упаковка на Windows:

```bash
python -m unittest discover -s tests/release -v
python scripts/release.py validate --version 2026.1.0-alpha.1
python scripts/release.py package --version 2026.1.0-alpha.1 --runtime win-x64 --updates
```

## Текущая граница поставки

Windows OfflineSetup.exe включает оригинальные .NET Runtime x64/x86 и модуль доступа к MDB через системный Jet x86; Office/Access Runtime не устанавливаются. Ручной ZIP без `--updates` остаётся framework-dependent сборкой для проверки и требует обе среды .NET на Windows; запуск Linux из исходников требует .NET и `mdbtools`. Установщик и дальнейшие обновления сохраняют внешнюю MDB/профиль. Основные рабочие сценарии реализованы; полевые проверки общей MDB, старой программы и целевых Windows продолжаются. Подробности сборки, проверки и ограничений — в [windows-installer.md](windows-installer.md).

Рабочая база, реальные спецификации, локальные профили и частные заметки не включаются в Git или ZIP. Исходный публичный WinForms-проект остаётся источником сравнения; новый репозиторий имеет собственную ветку `main` и независимые выпуски.

## Обновления из программы

Velopack NuGet и локальный CLI `vpk` закреплены на версии 1.2.0 (`Directory.Packages.props`, `.config/dotnet-tools.json`). Пакеты собираются на своей ОС с `--updates`. Автоматически выпускаются только четыре Windows-файла из [состава поставки](#состав-файлов-выпуска); `win-x64` и формат индекса не меняются. Для первоначальной раздачи предназначен OfflineSetup.exe, заранее устанавливающий обе среды .NET из вложенных файлов. Его внутренний Setup отдельно не публикуется; Windows portable пропускается через `--noPortable`. Linux AppImage и `releases.linux-x64.json` остаются доступными для ручной упаковки, требуют .NET 10 и mdbtools отдельно.

После публикации проверенного GitHub Release установленная программа находит его без GitHub-токена. По умолчанию используется стабильный `/releases/latest`, чтобы частые beta не вытесняли стабильный выпуск из первых десяти записей API. Тестовый канал включает prerelease, используя те же feed ОС/архитектуры; downgrade отключён. Выбор сохраняется в `Journal/update-settings.json` вне установки. Если файла ещё нет, установленная alpha/beta/rc начинает с тестового канала, стабильная версия — со стабильного; первый выбор сразу сохраняется. Явное отключение/включение важнее версии даже после обновления. Повреждённый/неизвестный профиль оставляет стабильный канал и пояснение в окне, без перезаписи файла; ошибка сохранения оставляет выбор в текущем сеансе и видимое пояснение, не мешая журналу. Перед публикацией нужно согласовать тег/версию пакета, флаг prerelease и описание в `docs/release-notes.md`. Не публиковать стабильный пакет под тестовым тегом или beta с флагом стабильного релиза. Пакеты и feed публикуются вместе; одного тега/ZIP недостаточно.

При включённой автопроверке после загрузки журнала проверяются только метаданные, затем проверка повторяется раз в 6 часов, пока не найдена новая версия. Фоновых скачиваний нет. Ручная проверка сдвигает следующую фоновую на 6 часов; общий признак занятости не позволяет пересекать проверку, загрузку и установку. Фоновая ошибка сети/тайм-аут записывается только в диагностический Trace, без изменения видимой ошибки или всплывающих окон; повтор — через 6 часов. Срок запроса ограничен 30 секундами. Один отменяемый таймер использует монотонное время; после сна нет накопления пропущенных попыток. Закрытие главного окна отменяет цикл и ожидание запроса. Уже найденный/загруженный пакет фоновые проверки не заменяют.

Колокольчик открывает окно с изменениями. Пользователь отдельно скачивает пакет и запускает установку с перезапуском. Velopack проверяет размер/хеш пакета; автоматическое применение при старте отключено. Ошибка проверки не мешает журналу; при ручной проверке она объясняется в окне обновлений. Результат перед перезапуском атомарно сохраняется в `Journal/update-restart.json` вне приложения и однократно восстанавливается; при MDB того же пути восстанавливаются и ID заявок последнего сформированного результата. Путь к MDB и настройки уже хранятся отдельно от установки.

До запуска Update.exe должны закончиться чтение/запись MDB, копирование, настройка экрана и работа других форм. Для Windows проверяются другие процессы той же установки. MDB внутри заменяемой папки приложения блокирует обновление: файл автоматически не перемещается. Полный установщик использует встроенный Jet через хост x86 и сохраняет Office; автоматическая установка Access Runtime не требуется. Ручная проверка рабочих Windows 10/11 и SMB остаётся отдельной задачей.

CI собирает реальные установочные артефакты Windows и запускает `scripts/test-update-install.ps1`: изолированная тестовая программа использует настоящий адаптер обновлений, устанавливается в случайную временную папку, обновляется с `2026.1.0` до `2026.2.0` и пишет результат после перезапуска. Перед запуском в тестовом источнике остаются только JSON-индекс и полные `.nupkg`, как в новом релизе. Проверяются восстановленный текст и неизменность искусственных внешних данных/настроек; рабочая MDB не используется. Прежний полный цикл выполнен в Windows CI; сокращённый набор должен пройти следующий Windows CI перед выпуском. Linux-сценарий `python3 scripts/test-update-install-linux.py` сохранён для ручного запуска, автоматический AppImage-цикл отключён.
