# Совместимость Access и настроек

## Режим эксплуатации

Пользователь подтвердил общую папку на одном компьютере и сетевой доступ клиентов. Windows 10 и 11 обязательны. Сохранить один существующий `OrderDB.mdb` и совместимость с прежними данными; чтение временной экспортированной копии не заменяет такую совместимость.

Использовать Windows-доступ через совместимый драйвер Microsoft как исходный вариант для сетевой записи. Старое приложение — .NET Framework 4.8, x86, `Microsoft.Jet.OLEDB.4.0`. Первый адаптер чтения нового приложения выбирает зарегистрированный ACE 16/12 текущей разрядности, Jet 4 допускается только в x86. В полном Windows-пакете интерфейс win-x64 и отдельный AccessHost win-x86; хост выбирает системный Jet первым, не меняя Office. Прямой ACE x64 остаётся вариантом разработки без вложенного хоста. Устройство и ограничения — в `docs/windows-installer.md`. Не считать Access автоматически кроссплатформенным из-за кроссплатформенного UI.

## Исключение для локальной разработки на Linux, 16.10.2026

Пользователь разрешил отдельную редактируемую копию реальной информации без Windows VM; на Windows сохраняется исходная MDB. `LocalJournalStore` хранит типизированную `OrderSummary` и все шесть прайсов в `.journal-test.json`, поддерживает создание с прежним расчётом, статусы и БЛЦБ. NULL/исторические значения сохраняются в представлении существующего read-адаптера; уже нормализованные им пустые текстовые поля не объявляются сырой копией всех Access-типов. Чтение исходной MDB — без записи, таблицы выгружаются из одного временного снимка. Повторный импорт не заменяет существующую локальную копию. Это не транзакционный снимок работающей общей папки и не новый Windows-контракт.

Пакеты проверяют только исходное изменяемое поле, затем заменяют локальный файл атомарно под общей блокировкой экземпляров. При конфликте требуется F5. ID и новые цены сохраняются между запусками, предыдущие суммы не пересчитываются. Локальные JSON/lock-файлы приватны и исключены из Git. Обратной синхронизации/экспорта в MDB нет. Подробности и ограничения — `docs/linux-local-copy.md`. Эта секция дополняет исторические этапы ниже: сама MDB на Linux остаётся read-only.

## Первый этап интеграции — только чтение, 16.10.2026

Пользователь поручил максимально ориентироваться на предоставленную настоящую `OrderDB.mdb`. `AccessOrderReader` загружает `Orders` по именам колонок и проверяет все 16 ожидаемых полей, включая пустую таблицу. Windows использует `System.Data.OleDb`, соединение `Mode=Read`, отключённое удержание в пуле и `SELECT`; Linux запускает `mdb-export` без shell. Выгрузка обрабатывается структурно, включая кавычки, переносы, Unicode, настоящий NULL и текст `"NULL"`. Чтение/открытие файла выполняется вне потока UI; неполный результат не подменяет прежний список. Для Linux это средство проверки и просмотра, а не транзакционная копия сетевой MDB при параллельной записи.

Дата и её исходное время, неизвестные толщина/цвет/длина/цена не подменяются нулём или сегодняшней датой. В read-модели дата отображается как DateOnly, исходное DateTime сохраняется отдельно. Пустые текстовые поля отображаются пустыми; это модель просмотра, а не готовая модель полной перезаписи записи. Исходная строка коэффициента сохраняется вместе с осторожно разобранными вспомогательными значениями; неизвестное значение не объявляется коэффициентом 1. Прайсы при чтении не используются. Список упорядочен по дате и затем ID по убыванию; это решение нового UI, не новое бизнес-правило.

Источник выбирается через «База данных» и хранится в локальном `Journal/data-source.json` отдельно от `ui-settings.json`. Путь сохраняется после успешной загрузки. Ошибка чтения или сохранения настроек оставляет прежний источник, список, выбор и результат. Ошибка при запуске с сохранённым путём не переключает приложение молча на демоданные. При настоящей смене источника очищаются результат, выбор и фильтры. MDB-доступ не реализует интерфейсы создания/массового изменения, поэтому эти команды недоступны; демохранилище остаётся отдельным режимом.

На Linux выполнены повторное чтение копии предоставленной базы, независимая сверка всех 16 полей с выгрузкой и проверка окна в обеих темах. Хеш оригинала и копии не изменился; частные результаты остаются в `.local/private-references/`. Проверка этого небольшого образца не доказывает производительность большой сетевой базы. Искусственный список из 5000 строк проверяет поиск и виртуализацию UI. В Windows CI предусмотрено создание искусственной Jet MDB через установленный ACE и отдельный тест типов/NULL/неизменности байтов; при отсутствии драйвера он явно пропускается. Ни эта проверка, ни сборка Windows не заменяет испытания реальной общей папки, Office-разрядности и старого EXE. Запись в MDB, прайсы, перенос конфига и установщик ещё не подключены.

При реализации учитывать блокировки Access, короткие транзакции, освобождение соединений, конфликт изменений и потерю связи. Проверка исходных значений при `UPDATE` может обнаруживать конфликт без добавления поля версии. Старая программа с безусловными обновлениями всё равно может перезаписывать чужие изменения; не обещать полную защиту без проверки всех писателей.

Прямую совместную запись через Jackcess не принимать за эквивалент Jet/ACE: библиотека не обеспечивает совместимость транзакций/блокировок с параллельными писателями. Иной способ доступа требует отдельной проверки именно сетевого многопользовательского сценария.

## Второй этап — статусы и БЛЦБ, 16.10.2026

В рамках поручения продолжить разработку добавлен `OleDbOrderBatchEditor` для Windows. Это заменяет ограничения первого этапа относительно **этих двух операций**. Чтение остаётся отдельным read-only соединением; запись открывает `Mode=19` (ReadWrite + Share Deny None) без удержания в пуле, проверяет исходное значение изменяемого поля и сохраняет весь пакет одной транзакцией. Создание/полное редактирование/удаление заявок и расчёты ещё не подключены. На Linux MDB остаётся только для чтения, без отдельного механизма записи.

`IOrderBatchEditor` принимает исходные `OrderSummary`, а не только ID. `DeliveryNumber` в модели теперь nullable: NULL и пустая строка различаются для проверки конфликта, в UI обе отображаются пустыми. Очистка номера сохраняет NULL. Поле сравнивается бинарно через `StrComp(..., 0)` в WHERE, включая регистр и конечные пробелы; параметры передаются типизированно и по порядку OLE DB, без конкатенации пользовательского номера. Повторяющиеся ID с разными исходными значениями отклоняются; порядок блокировок — по ID. Изменение другого поля другим клиентом само по себе не считается конфликтом; при успехе оно возвращается в UI с актуальным значением. Номер/дата, суммы, коэффициенты, прайсы и схема не перезаписываются.

Конфликт/удаление или ошибка SQL откатывают весь пакет, в том числе уже выполненные в нём UPDATE. Результирующие строки читаются до commit; после подтверждённого commit нет дополнительных запросов. Если commit/rollback нельзя подтвердить, возвращается `OutcomeUnknown`: изменения могли примениться, поэтому повторные записи блокируются до успешного F5, текст формы/результата и выбор сохраняются. При конфликте также требуется F5. При подтверждённом отказе можно повторить действие. Ошибка обновления UI после успешного commit сообщается как проблема экрана, а не как несохранённые данные. Дополнительной автоматической отправки или повторов нет. Это проверка значения поля, без нового поля версии; возврат к прежнему значению и последующие безусловные записи старого клиента всё ещё возможны.

В Windows CI добавлен отдельный тестовый проект `Jornal.Access.Tests` без Avalonia и обязательный контур Jet/ACE x86 (SDK x86, системный 32-разрядный PowerShell, искусственная Jet MDB). Он не меняет win-x64 поставку и не устанавливает Office/ACE на компьютеры пользователя. Каждая проверка пишет только в свою временную копию; фикстура и рабочая база не используются для записи. Проверяются повторное чтение, все остальные поля и схема, Currency/NULL, параметризация, регистр/пробелы, откат после позднего конфликта/удаления/ошибки второго UPDATE и два конкурирующих соединения. Отсутствие провайдера или фикстуры в обязательном контуре приводит к ошибке, не к пропуску. На Linux эти нативные тесты явно пропускаются. ACE x64-проверка остаётся дополнительной и условной. На Windows CI 16.10.2026 все 10 транзакционных сценариев прошли через Microsoft.Jet.OLEDB.4.0; проверка реальной общей папки, Office и старого EXE остаётся отдельной. Дополнительно проверяются пути с пробелами, апострофом и точкой с запятой.

Наблюдение диагностики на англоязычном Windows runner: Jet x86 отклоняет кириллический путь с `Not a valid file name`, тогда как кириллические данные внутри базы читаются/записываются. Переименование/перенос рабочей базы автоматически не выполняются. Поэтому нативные транзакционные фикстуры создаются в ASCII-папках; поддержку кириллических/сетевых путей через ACE x64 следует подтвердить на целевой Windows. `Mode=Read` открывается у Jet, числовой `17` им отклонён; для записи проверен `Mode=19`.

## Структура существующей базы

Схема исследована на копии предоставленного файла. Рабочая MDB и конфигурация не публикуются. Частные пути, хеш образца и точные результаты исследования сохранены локально в `.local/private-references/data-contract.md`; этот файл может отсутствовать после клонирования репозитория.

### `Orders`

Поля перечислены по выгруженной схеме. Старый UI использует числовые индексы колонок; не переносить зависимость от их порядка, работать по именам.

| Поле | Тип Access / назначение |
| --- | --- |
| Код | AutoNumber / Long Integer, первичный ключ |
| Дата | DateTime, дата из заголовка спецификации |
| Менеджер | Text(255) |
| Спецификация | Text(255), старое представление `MMDD-номер` |
| Заказчик | Text(255) |
| Вид_резки | Text(255) |
| Марка_стали | Text(255), фактически произвольный материал |
| Размер_листа | Text(255), например `1500x6000` |
| Кол_во_листов | Text(255), несмотря на числовой смысл |
| Стоимость | Currency |
| Толщина | Double |
| Ход | Long Integer, длина в метрах после старого округления |
| Вес | Text(255), встречается десятичная точка |
| БЛЦБ | Text(255), номер реализации, может отсутствовать |
| Color | Long Integer, ARGB, default `-1` |
| Коэффициент | Text(255), составное/старое значение, возможен NULL; в схеме default `1` |

Уточнение пользователя для нового импорта 16.10.2026: если размеров несколько, перечислять их через запятую в существующем `Размер_листа`, а в `Кол_во_листов` сохранять общий итог. Размеры имеют одну толщину, перечень не превышает 255 символов; превышение/разные толщины не усекаются и не выбираются молча. Старый код читает/редактирует/выводит размер как текст, расчёт использует отдельно толщину, ход и коэффициент. Схема и типы остаются прежними; это не подтверждение прогона старого EXE по сети. Все отдельные размеры/количества сохраняются в отчёте парсера, не в новой колонке MDB.

Уточнение 17.10.2026: HTML-импорт заполняет целое положительное общее количество. Ручной ввод может быть дробным (запятая/точка), нулём или числом со знаком по необходимости пользователя; это одна десятичная запись, без выражений и слов. `Кол_во_листов` остаётся Text(255), на ручное значение не накладывается Int32-ограничение счётчика парсера. Старая программа сохраняет и выводит поле как строку (`MainForm.cs`: создание/редактирование и результат); в расчёте цены поле не участвует. Новая валидация применяется к создаваемому/изменяемому количеству; чтение, архив и восстановление сохраняют исходный текст/NULL. Это сверка исходного кода, а не выполненный прогон старого EXE на Windows.

Поля `Стоимость`, `Толщина`, `Ход` имеют в исследованной схеме default `0`. Существующие значения и NULL учитывать независимо от defaults новых записей.

### Статусы и составной коэффициент

| Смысл | Значение `Color` |
| --- | --- |
| В работе | `-882036` |
| Готово | `-10238087` |
| Отгружено | `-8154114` |
| Без назначенного цвета | `-1` |

Допускаются любые пользовательские ARGB-цвета. В присланном конфиге начальный цвет `-16711936`; это не один из трёх фиксированных статусов.

Старый код читает формы коэффициента `коэффициент|детали|пробивки` и `коэффициент|детали|пробивки|ID|газ`. Поддержать также NULL/пустое и старое одиночное число. При создании из ручного ввода составные данные могут быть неполными; заранее не считать все записи пятичастными. Значения `-1` используются как отсутствие вспомогательных сведений. В HansLaser-строках вокруг `|` могут быть пробелы.

Внутри новой модели это могут быть отдельные поля; адаптер отвечает за совместимое чтение/запись. Не переписывать старые строки только при просмотре.

### Прайсы

`PriceLM500`, `PriceLL500`, `PriceP`, `PriceG`, `PriceHL_id1`, `PriceHL_id2`. Имена колонок — толщины, в том числе `0,5`, `0,8`, `1,2`, `1,5`, `2,5`; значения — Long Integer. Старый код читает первую строку. Доступность тарифа и диапазон допустимой толщины в коде — разные ограничения.

В исследовании обнаружены исторические суммы, отличающиеся от расчёта по текущему прайсу при пустом коэффициенте. Причина не установлена: это могут быть прежние тарифы или исторические правила. NULL не объявлять коэффициентом 1 автоматически; не пересчитывать сохранённые суммы при просмотре. Точные значения остаются в частных локальных заметках.

## Чтение прайсов и расчёт — 16.10.2026

Добавлены `IPriceReader` / `AccessPriceReader`, OLE DB и Linux MDB Tools; в установленном Windows-комплекте — новая read-only операция хоста x86 `ReadPriceTable` (добавлена в конец enum, прежние значения протокола 1 сохранены). Читается только первая строка выбранной таблицы из фиксированного списка шести прайсов, без SQL из пользовательских полей и без записи. NULL/отсутствующий тариф отличаются от нуля; неоднозначные дробные колонки отклоняются. Экспорт прайсов на Linux использует табуляцию, поскольку MDB Tools не экранирует запятые в числовых заголовках. `Orders` сохраняет прежний CSV-контракт.

`CuttingPriceCalculator` сохраняет выбор прайса/ID, диапазоны станков, Double и ToEven старой формулы. Коэффициент пробивок сверяется с исходным классом. Исторические суммы не пересчитываются; минимальная сумма письма остаётся отдельным правилом. Команды `Jornal.Inspect prices` / `price` позволяют проверить модуль. Создание/редактирование MDB и подключение расчёта к форме ещё впереди. Полный контракт и проверки — [docs/pricing.md](../../../../docs/pricing.md).

## Конфигурация

- `connectionStrings/pathdb`: строка OLE DB с путём к существующей MDB. Путь может указывать на Release даже при предоставлении конфигурации из Debug; это не доказательство ошибки.
- `appSettings/Managers`: список подсказок менеджеров через запятую.
- `appSettings/Customers`: список подсказок заказчиков через запятую.
- `appSettings/TechnologColor`: начальный цвет новой заявки.

Поддержать перенос этих настроек и настройку пути к общей базе. Полный Access/Office как пользовательский интерфейс не является функцией приложения; необходимые драйверы и их установку проверить отдельно.

Пользователь подтвердил единый установщик со всеми необходимыми компонентами; подробности поставки находятся в разделе «Выбранная технология и поставка» файла [requirements.md](requirements.md). Учитывать существующий Office и разрядность его компонентов при выборе драйвера. Сетевой путь и возможность чтения базы проверять без тестовой записи в рабочие данные. Установка и обновление сохраняют существующие MDB и настройки.

## Граница работ с данными

Для исследования, проверки миграции кода и тестовой записи работать с копией. Исходные файлы пользователя не включать в публичный репозиторий автоматически. Любое будущее изменение схемы, замена СУБД, синхронизируемая вторая база или хранение новых полей требует отдельного решения в рамках конкретной задачи.

Обязательное уточнение пользователя 16.10.2026: не менять MDB так, чтобы нарушить обратную совместимость с первой старой программой. Схема/типы/ключи/форматы полей сохраняются, служебные таблицы и признаки корзины в MDB не добавляются.

## Редактирование и корзина, 16.10.2026

`OrderRecord` хранит точные типизированные значения всех 16 полей, включая текстовые NULL, Double, DateTime со временем и Currency. `IOrderMaintenance` читает полную строку, выполняет UPDATE/DELETE с проверкой всего снимка и восстанавливает свободный исходный ID/все поля без пересчёта цены. Редактирование пересчитывает цену по текущему прайсу и требует проверки новой суммы. Значения протокола 0–5 сохранены, новые операции: ReadOrder=6, UpdateOrder=7, DeleteOrder=8, RestoreOrder=9. Ответ полной записи должен иметь явное подтверждение и соответствовать запросу; повреждённый ответ отправленной записи — OutcomeUnknown.

Полный локальный архив сохраняется/проверяется до каждого DELETE. Общая выбранная группа состоит из независимых операций, останавливается на первой ошибке и показывает итог каждой; общей транзакции группы нет. Pending-состояния сверяются чтением без повтора записи, не удаляются по сроку; занятый ID не перезаписывается. Подтверждённые копии хранятся 30 дней. Неизвестная расширенная схема и входящие связи к Orders отклоняются для удаления; база не меняется. Linux-копия повторяет сценарий, сохраняя полные затронутые записи в необязательном Records; прежняя нормализация импорта не восстанавливается. Ограничения пути/локального профиля и проверки — [order-maintenance.md](../../../../docs/order-maintenance.md).

## Офлайн-установщик и хост x86, 16.10.2026

Пользователь поручил полный установщик и подтвердил работу старой программы с той же MDB на целевых компьютерах. Решение реализации: Inno Setup оборачивает per-user Velopack, включает оригинальные .NET Runtime x64/x86 и предварительно проверяет системный Jet через AccessHost x86; Office/ACE не устанавливаются и не перенастраиваются. Хост переиспользует чтение и транзакции существующего адаптера. Один запрос/ответ UTF-8 JSON на процесс, поля/NULL/Currency сохраняются; тайм-аут/обрыв после отправки записи требует F5 как OutcomeUnknown. Рабочая MDB не включается в установщик, её путь выбирается в приложении и хранится отдельно. Чистая офлайн-VM, системная кодировка пути и совместная работа со старым EXE/SMB требуют ручной проверки. Подробная проверка Windows CI описана в `docs/windows-installer.md`.

## Третий этап — создание заявки в MDB, 16.10.2026

Пользователь поручил этап «Создание заявки с расчётом и сохранением в MDB». Windows-источник подключает `IManualOrderCreator` и `IPriceReader` через `AccessHostClient` или прямой `OleDbManualOrderCreator`; Linux MDB остаётся read-only. Добавлена операция `CreateOrder` со значением 5, значения 0–4 не менялись. В транзакции читается прайс, проверяется просмотренная цена, выполняется типизированный INSERT, отдельно `@@IDENTITY`, затем сверка строки до commit. Изменение прайса не создаёт запись и требует нового ручного сохранения после просмотра цены. Дата, Currency, Unicode, исходный коэффициент и NULL БЛЦБ сохраняются в прежней схеме. `ManualOrderDraft` содержит общую валидацию/формирование записи, необязательные просмотренную цену и начальный цвет; форма пока использует цвет -1, перенос TechnologColor остаётся отдельной задачей.

При неизвестном исходе хоста/commit повтор блокируется до F5; ввод восстанавливается при следующем открытии формы в текущем сеансе. Пользователь должен проверить, не появилась ли запись; уникальность номера спецификации не предполагается, автоматического повтора нет. Linux-копия повторяет этот контракт без MDB-записи. Полный сценарий и границы — `docs/manual-orders.md`. Редактирование, удаление, парсер, старый конфиг и SMB/старый EXE требуют следующих этапов/ручных проверок.


## Подключение HTML-импорта к созданию, 16.10.2026

`ManualOrderDraft` дополнен необязательными PartCount/PunchCount; они передаются по прежнему CreateOrder и сохраняются только в существующих сегментах коэффициента, без новой операции/колонки.
