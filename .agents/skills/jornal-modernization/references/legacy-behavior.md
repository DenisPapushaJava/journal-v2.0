# Исходное поведение и матрица переноса

Источник — код коммита `03b2388`, изученный 15.10.2026. Старая программа в этой сессии на Windows не запускалась. Ниже описан код, а не гарантированная безошибочность каждой ветки.

## Карта исходников

Пути относительно корня репозитория:

- `Program.cs`: запуск `MainForm`, обработчик UI-исключений, `error.log`.
- `MainForm.cs`: таблица, запросы Access, создание/редактирование, цены, статусы, вывод и буфер обмена.
- `Form1.cs`: класс `Form_NewOrder`, поля заявки, импорт и `Button_RunClick` — основной парсер.
- `Clasess/ExtractText.cs`: извлечение PDF через iTextSharp и HTML через HtmlAgilityPack.
- `Clasess/CalculationCoefficient.cs`: соответствие пробивок/деталей коэффициенту.
- `Clasess/IdMaterialPrice.cs`: выбор прайса HansLaser по ID материала.
- `Add_BLCB.cs`: диалог номера реализации/БЛЦБ.
- `Clasess/ButtonNewOrderStyleManager.cs`: визуальные состояния кнопки при drag-and-drop.
- `MainForm.Designer.cs`, `Form1.Designer.cs`: привязки событий и доступные действия.
- `Form3.cs` не включён в `Jornal.csproj`; не считать пустую форму реализованной бизнес-функцией. `LoadForm` служит заставкой.

## Текущий парсер

### Подготовка текста и маркеры

- PDF читается iTextSharp, постранично, `SimpleTextExtractionStrategy`. При импорте файла загрузчик добавляет `*` перед извлечённым текстом.
- HTML читается HtmlAgilityPack: удаляются `script/style`, берётся `InnerText`, декодируются сущности, пробелы/табуляции/переносы схлопываются. Загрузчик добавляет ведущий пробел.
- Drag-and-drop допускает `.pdf`, `.html`, `.htm`, но текущие загрузчики извлекают HTML только при расширении `.html`. Обработку `.htm` учитывать как исправление несогласованности ввода. При перетаскивании нескольких файлов фактически используется первый; полноценный пакетный импорт пока не реализован.
- `Button_RunClick`: `@` или `*@` ведёт в HansLaser; ведущий пробел — в ветку Wintech; оставшийся текст — в ветку копирования из браузера.
- Пользователь подтвердил намеренность признаков станка и их влияние на цену. Учитывать отдельно признак из документа и технический префикс загрузчика: `*` сам по себе добавляется программой, а не извлекается из PDF.
- Текущая маршрутизация — исходная точка совместимости. Не заменять её выводом по папке, толщине или произвольному слову из имени детали. Неизвестное/противоречивое определение станка должно диагностироваться.

### БЛОК / Wintech и браузерный текст

- Габариты ищутся после `Габариты:` и делятся по `x`: толщина, длина, ширина. Размер листа в форме собирается как ширина `x` длина; например, `6.0x6000x2000` даёт `2000x6000`.
- Толщина в старом коде дополнительно делится по точке. Целое `6` вызывает проблемы; новая реализация должна понимать `6`, `6.0`, `6,0` при сохранении значения.
- Марка берётся из первого токена после `Материал:` с учётом пробелов/табуляций ветки. Правило пользователя «материал без пробелов» уже используется старым кодом.
- Длина ищется после `реза:`; вес — после первого `кг`; листы — после `Листов:`. Поиск выполняется по всему плоскому тексту, что объясняет риск совпадений в названиях.
- Детали и пробивки читаются из `Общие кол-во деталей:` и `Пробивки:`. Для расчёта используются итоги заказа.
- Номер и дата извлекаются из строки после `Спецификация №` в заголовке. Вариант пустого элемента после разделения по `-` обрабатывается отдельно.
- Номер в журнале преобразуется в `MMDD-номер`, например, `2026-03-26-1130` даёт `0326-1130`; дата — `26.03.2026`. Исходный идентификатор задаёт программа раскладки, новый журнал его не генерирует.
- Вид резки определяется по `ЛАЗЕР`, `ПЛАЗМА`, `ГАЗО-КИСЛОРОДНАЯ` в тексте до `.rcam`. Для других расширений глобальный поиск становится ещё менее ограниченным.

### HansLaser

- После деления текста по переносам используются фиксированные индексы: имя заказа/дата `[10]`, детали `[11]`, листы `[13]`, вес `[15]`, пробивки `[16]`, длина `[17]`.
- Строки материала/габаритов/газа зависят от способа импорта: блок `[30]` или `[25]`, толщина при файловом импорте `[29]`, газ `[31]`.
- `марка_ID` делится по `_`; исходная семантика ID: `0` — чёрная сталь, `1` — нержавеющая, `2` — цветной металл; `-1` — default. Сохранять исходную марку и служебный ID раздельно во внутренней модели. Дополнительные `_` требуют проверки по новым примерам, а не слепого удаления части марки.
- Размер листа также выводится ширина `x` длина. Газ сохраняется в составе вспомогательных данных.
- Длинные имена и переносы могут сместить индексы; переносить следует смысл полей, а не номера строк.
- Старый парсер не извлекает время резки ни в одной ветке.

## Расчёт и чувствительные к совместимости особенности

### Длина и цена

- БЛОК: отбрасывается дробная часть миллиметров, затем целочисленное `мм / 1000 + 1`. Это даёт лишний метр для точного кратного 1000; не менять такую особенность незаметно вместе с переписыванием парсера.
- HansLaser: `Ceiling(мм / 1000)`.
- Стоимость: `Math.Round(тариф × длина_м × коэффициент)` без явного `MidpointRounding`.
- Вес и количество листов прямо на эту формулу не умножаются. Не добавлять множитель количества листов: в спецификации уже может быть общая длина.
- В прайсе выбирается первая строка и колонка с именем толщины, например `2,5`.

| Вид резки | Проверка толщины в текущем коде | Прайс |
| --- | --- | --- |
| Лазер | `<= 20` | `PriceLL500` |
| Плазма | `2..32` включительно | `PriceP` |
| Газо-кислородная | `16..200` включительно | `PriceG` |
| HansLaser | `<= 60` | ID `1` → `PriceHL_id1`, ID `2` → `PriceHL_id2`, остальные → `PriceLL500` |

`PriceLM500` присутствует в образце базы, но актуальный `NewOrd/Edit` его не выбирает. Не удалять таблицу и не менять выбор прайса из-за похожего названия.

### Коэффициент

Сначала `p = Math.Round(пробивки / детали)`; затем `CoefficientOfPunch(p)`. В обычном режиме .NET середины округляются к ближайшему чётному. Отдельно обрабатывать некорректные/нулевые количества; падение старого кода не является бизнес-правилом.

| Округлённое отношение `p` | Коэффициент |
| --- | --- |
| До 1 включительно | 1.0 |
| 2..10 | 1.1, 1.2, …, 1.9 соответственно |
| >10..15 | 2.0 |
| >15..20 | 2.1 |
| >20..30 | 2.2 |
| >30..40 | 2.3 |
| >40..50 | 2.4 |
| >50..60 | 2.5 |
| >60..70 | 2.6 |
| >70..80 | 2.7 |
| >80..90 | 2.8 |
| >90..100 | 2.9 |
| >100 | 3.0 |

### Исторические суммы и вывод

- `PrintResult` поднимает отображаемую стоимость каждой строки до 500 ₽, но сохранённое значение в базе может быть меньше. Это различие нужно явно учесть до унификации расчёта.
- Чтение/обновление списка не должно пересчитывать сохранённые суммы по текущему прайсу.
- При редактировании старый код пересчитывает стоимость; сохранять это поведение как исходное, отдельно проработав безопасный и понятный пользователю пересчёт истории.
- Формат строки результата: лист/толщина/размер, материал, количество листов, вес, цена, вид резки.
- Обычный комментарий использует полный БЛЦБ и требует длину больше пяти символов. Telegram-комментарий использует последние пять символов и убирает ведущие нули. Проверку и форматирование номера реализации учитывать отдельно.
- Текущий Telegram-комментарий берёт БЛЦБ текущей строки для группы выбранных строк. Смешанные реализации/заказчики требуют отдельного решения, а не молчаливого объединения под одним номером.


## Перенос расчёта — первый этап 16.10.2026

Выделены чтение первой строки прайса и чистый `CuttingPriceCalculator`, сохранены выбор станка/ID, диапазоны, Double и округление ToEven. Таблицы читаются по именам, колонки толщины нормализуются с проверкой неоднозначности. `PriceLM500` не включается в выбор автоматически. Шкала коэффициента проверяется напрямую по исходному `CalculationCoefficient`, а выбор HansLaser — по `IdMaterialPrice`; эти два старых файла компилируются только в тестовую сборку как независимый эталон. Формула проверена также на случаях, где decimal меняет итог на рубль. Длина принимается уже в целых метрах; правила перевода миллиметров остаются частью будущего импорта. UI/сохранение заявок и старый EXE этим ещё не проверены. Контракт — `docs/pricing.md`.

## Перенос результата — 16.10.2026

В новом журнале реализованы формирование выбранных заявок, ручное редактирование текста, очистка с сохранением выбора и копирование Unicode/RTF/HTML. Уточнение пользователя 17.10.2026 (UX-28) явно заменяет прежнее накопление: каждое нажатие «Результат» заменяет текст всеми текущими выбранными заявками, отсортированными по числовой толщине, затем материалу. Состав строк и порядок таблицы сохраняются. Выбор сопоставляется по ID с актуальными видимыми данными; одинаковый ID включается один раз. Смена выбора сама по себе результат не меняет, ручные правки сохраняются до следующего формирования. Формат обычной строки и пакетные отступы повторяют `PrintResult`; минимум 500 ₽ и округление к чётному действуют только в выводе, сохранённая стоимость не пересчитывается. Currency форматируется без ограничения Int32. Набор с неизвестной стоимостью отклоняется целиком; прежний результат остаётся.

Исходный `richTextBox_Result` был редактируемым, Times New Roman 12 pt, красный текст (`MainForm.Designer.cs:584`). По уточнению пользователя подготовку для почты можно улучшить: По уточнению пользователя 17.10.2026 HTML/RTF используют выбранные размер/цвет (начальные Arial 10 pt и мягкий красный), независимо от темы окна; HTML выравнивает поля по ячейкам. Компактные настройки, серый фон редактора и хранение вне MDB — UX-27. Обычный Unicode-текст сохраняет прежние подписи и разделители. HTML/RTF — альтернативные представления одного текста, автоматически почта не отправляется. Операции с MDB этим не подтверждаются; настоящая вставка в используемый Windows-почтовый клиент ещё не проверена.


## Перенос массовых действий — 16.10.2026

В демохранилище реализованы `IOrderBatchEditor.SetColorAsync` и `SetDeliveryNumberAsync`. Три кнопки статуса используют прежние ARGB: `-882036`, `-10238087`, `-8154114`; снятие цвета записывает `-1`. Изменяется только выбранное поле выбранных ID. Пакет проверяется до изменения; блокировка демохранилища исключает чтение промежуточного состояния. Стоимость и прочие поля остаются прежними. F5 перечитывает изменения текущего сеанса; реальная MDB не открывается.

Форма БЛЦБ показывает все выбранные спецификации, подставляет общий номер и явно сообщает о разных исходных номерах. В отличие от старой подстановки номера активной строки, смешанное выделение не предлагает незаметно заменить все значения одним существующим номером. Пустое поле при смешанных номерах само по себе не включает сохранение; есть явная очистка. Демохранилище сохраняет произвольный текст номера (в том числе апострофы); ограничение — одна строка до 255 символов, по схеме Access. Отмена не пишет, Enter сохраняет, ошибка оставляет ввод для повтора.

Видимые строки обновляются без замены их объектов; фильтры/сортировка и выделение по ID согласуются после записи. Изменённая запись может исчезнуть из фильтра. В отличие от побочной очистки `ClearTextResult` старого `AddBLCB_In_DB/UpdateDataGrid`, готовый результат сохраняется. На время записи блокируются конфликтующие действия и закрытие окна. Произвольная палитра и режим «Код цвета» пока не перенесены. Сетевая запись Access требует отдельного транзакционного адаптера и Windows-проверки.

## Первый HTML-профиль нового парсера, 16.10.2026

`block-html/v1` извлекает поля по роли таблицы/подписям и сохраняет источники каждого значения; глобальные Split и фиксированные индексы старого кода не переносятся. Материалы сверяются между деталями, итоговые числа не заменяются суммой деталей. Номер/дата берутся из заголовка, вид резки — из явной метки после идентификатора, расширение/внешнее имя файла их не определяет. Нормализация отдельно сохраняет прежние метры БЛОК и расчёт коэффициента общим модулем. Уточнение пользователя: несколько размеров одной толщины перечисляются через запятую в существующем Text(255), общее количество листов и итоги не разбиваются. Это улучшение нового парсера; старый размер был текстом, не входившим в расчёт цены. Все варианты/количества и источники сохранены в отчёте, несовместимые толщины/длина поля диагностируются. Поддержка длительности добавлена как отдельный необязательный факт без MDB-поля. Реализация пока в библиотеке/CLI; импорт в UI, PDF/текстовый профиль и старый EXE требуют следующих шагов. Проверенный корпус и границы — `samples.md`, полный контракт — `docs/specification-import.md`.


## Подключение HTML-профиля к форме, 16.10.2026

Реализованы перетаскивание одного HTML/HTM с оверлеем и отменой, выбор HTML в форме, частичное заполнение с диагностикой/источниками и ручная проверка перед добавлением. ## Перенос PDF HansLaser, 17.10.2026

Профиль `hans-pdf/v1` заменяет фиксированные номера строк старой HansLaser-ветки на геометрию текста и подписи полей/колонок. Сохраняются номер/дата из заказа, формат `MMdd-номер`, Double/Ceiling для миллиметров, общая шкала коэффициента, ID/прайс и прежние сегменты сохранения. Последний подтверждённый `_ID` отделяется от марки; дополнительные `_` в названии больше не отбрасываются. Газ читается отдельно, не выводится по ID. Количество по строкам листов сверяется с итогом; дополнительные страницы деталей не заменяют шапку. Частичный разбор оставляет недостоверные поля пустыми с источниками; отсутствие ID не приводит к расчёту по стандартному прайсу без проверки пользователя. Сам импорт не сохраняет запись, дальше действует прежний `ManualOrderDraft`/транзакция. Контракт — `docs/hans-pdf-import.md`, корпус/границы — `samples.md`. Это новый профиль и автоматические проверки, не запуск старого EXE/общей папки на Windows.

## Перенос буфера обмена — UX-48, 17.10.2026

Обычный комментарий сохраняет прежний текст для одной выбранной строки. Telegram сохраняет подписи/порядок станков, но по последующему уточнению убирает `**` и сортирует толщины численно внутри каждого станка по возрастанию; разделяет менеджеров/заказчиков вместо CurrentRow и последнего клиента; новые станки включаются автоматически. Папки теперь строятся непосредственно из снимка, с предпросмотром, безопасными/уникальными именами, копированием в проводник и очисткой только собственных пустых наборов. Контракт — docs/clipboard.md; настоящая вставка Windows/Nemo требует ручной проверки.
